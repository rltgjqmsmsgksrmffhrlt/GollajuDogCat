# data/generated_v2 — Kaggle 실측 기반 재보정 데이터셋

> 🔰 데이터 만드는 게 처음이라면 [`docs/데이터_만들기_가이드.md`](../../docs/데이터_만들기_가이드.md) (목적 정하기부터 결과물까지)
> · 스크립트를 직접 돌린다면 [`docs/데이터_파이프라인_운영_가이드.md`](../../docs/데이터_파이프라인_운영_가이드.md) (기술 상세)

`data/generated/`(v1, 원본 팀 산출물)는 그대로 보존하고, 같은 A/B 테스트 시나리오를
**공개 이커머스 데이터(Kaggle)로 검증 가능한 부분은 실측값으로 대체**하고, 검증 불가능한
부분은 "가정(명시)"로 표시해 다시 생성한 버전입니다. 생성 스크립트는 `scripts_v2/`.

## 데이터 개요

- **기간**: 2026-09-08 ~ 2026-12-06 (90일)
- **규모**: A/B 그룹 각 9,500명 (총 19,000명), 90일간 순차 유입 — v0.3까지는 각
  2,500명(총 5,000명)이었으나, 통계적 검정력이 부족해(아래 "v0.4 표본 확대" 절 참고)
  v0.4에서 3.8배로 늘렸습니다.
- **생성 규모**: 이벤트 로그 640,200건(약 64만 건), 주문 1,342건
  (v1은 조회 시 100% 장바구니 담기 가정으로 주문이 약 1.2만 건까지 부풀려졌으나,
  v2는 이 가정을 제거해 실제 이커머스 조회→구매 전환율에 가까운 규모로 줄었습니다.
  자세한 배경은 아래 "왜 다시 만들었나" 참고. v0.3에서 파이프라인 버그 2건을 고치고
  재생성해 v0.2 시점(345건)보다 소폭 늘었고, v0.4에서 표본을 3.8배로 늘려 다시
  늘었습니다 — 아래 "v0.3 파이프라인 버그 수정"·"v0.4 표본 확대" 절 참고.)
- **기준치 산출 방법**: 세션 단위 이벤트 로그를 제공하는 3개 데이터셋(REES46,
  Cosmetics Shop, RetailRocket)에서 '조회 → 장바구니 → 구매' 전환율을 직접 집계한 뒤,
  그 중앙값(조회→장바구니 3.60%, 장바구니→구매 32.83%)을 시뮬레이션 확률로 채택했습니다.

## 왜 다시 만들었나

골라주개냥 팀은 앱을 실제로 만들기 전에, "이 앱을 운영하면 어떤 데이터가 쌓이고,
우리 가설(맞춤 추천을 보여주면 사람들이 더 잘 산다)이 맞을지"를 미리 확인하고
싶었습니다. 그래서 수천 명의 가짜 유저가 90일 동안 앱을 쓴다고 가정하고, 컴퓨터로
그 행동 데이터를 통째로 시뮬레이션했습니다(이게 v1입니다).

그런데 v1을 만들 때 이런 가정이 들어갔습니다: **"유저가 상품 상세 페이지를 한 번이라도
보면, 무조건 장바구니에 담는다."** 실제 쇼핑 경험을 떠올려 보면 이상한 가정입니다 —
대부분은 구경만 하고 장바구니에 안 담으니까요.

왜 이런 가정을 넣었을까요? 원본 계획서에는 두 개의 목표 숫자가 있었습니다.
- "장바구니에 담았는데 안 산 사람의 비율(이탈률)"은 40%가 되어야 한다
- "추천 상품을 보고 실제로 산 비율(전환율)"은 3.3%가 되어야 한다

문제는 이 두 숫자가 서로 다른 출처(하나는 "이커머스 업계 전체 평균", 하나는 "반려동물
카테고리 평균")에서 가져온 거라, 같은 유저 그룹 안에서 두 숫자를 동시에 정확히 맞추는
게 수학적으로 불가능했습니다. 팀도 이걸 알았는지 코드 주석에 스스로 "이건 근사치입니다"
라고 적어뒀습니다. 억지로 두 숫자를 맞추려다 보니 "조회하면 100% 장바구니 담기"라는,
현실과 동떨어진 가정이 만들어진 겁니다.

그래서 저희는 이렇게 접근을 바꿨습니다: **목표 숫자를 억지로 끼워 맞추는 대신, 진짜
쇼핑몰에서 상품을 본 사람 중 몇 %가 장바구니에 담고, 담은 사람 중 몇 %가 실제로
사는지 — 그 진짜 비율을 알아내서 쓰자.**

이 진짜 비율은 우리가 지어낼 수 없는 값이라, 실제로 공개된 이커머스 로그 데이터
(Kaggle)를 찾아봤습니다. 한 명의 유저가 앱을 켜서 끌 때까지의 행동이 세션 단위로
기록된 데이터셋 3개(REES46, Cosmetics Shop, RetailRocket)를 확인해보니:
- REES46: 조회한 사람 중 **3.60%**가 장바구니에 담고, 담은 사람 중 **45.96%**가 구매
- Cosmetics Shop: **59.87%**가 담고, **22.31%**가 구매
- RetailRocket: **2.58%**가 담고, **32.83%**가 구매

Cosmetics Shop의 59.87%는 다른 두 곳보다 10배 넘게 높은데, 화장품 쇼핑몰 특성상
장바구니를 위시리스트처럼 쓰는 습관 때문으로 보입니다. 이런 특이값이 섞이면 평균을
낼 때 전체 숫자가 왜곡되므로, 평균 대신 "가운데 값(중앙값)"을 썼습니다 —
조회→장바구니 **3.60%**, 장바구니→구매 **32.83%**.

이 두 숫자를 시뮬레이션에 그대로 넣었습니다. "조회하면 100% 담는다"를 버리고,
"조회한 사람 중 3.60%만 담고, 담은 사람 중 32.83%만 산다"로 바꾼 겁니다. 그러자
장바구니 이탈률과 구매전환율은 더 이상 억지로 맞춰야 할 목표가 아니라, 이 두 확률에서
자연스럽게 나오는 결과값이 됐습니다 — 서로 모순될 일이 없어진 거죠.

다만 부작용도 있습니다. 조회하면 무조건 담던 v1에서는 주문이 약 1만 2천 건 나왔는데,
진짜 비율을 쓰니 v0.2 시점엔 345건까지 크게 줄었습니다. "데이터가 줄어서 문제
아닌가" 싶을 수 있지만, 오히려 이게 실제 이커머스의 조회→구매 전환율(보통
0.8~13% 사이)에 훨씬 가까운, 더 현실적인 숫자입니다. 이후 v0.3에서 파이프라인
버그를 고치며 381건으로, v0.4에서 통계적 검정력 확보를 위해 표본을 3.8배로
늘리며 1,342건으로 늘었습니다(현재 값).

## A/B 처치 효과 가정 (LIFT = +15%)

"맞춤 추천 노출이 선택 피로를 줄이고 전환을 높인다"는 우리 서비스의 핵심 가설은
Kaggle 어떤 데이터셋에도 대응물이 없는, 우리만의 미검증 가설입니다. v1은 지표마다
서로 다른(때로는 2배 가까운) 임의의 격차를 발명해 사용했습니다. v2는 이를 하나의
보수적인 가정 계수로 통일했습니다.

- **+15% 상대 개선**을 채택했습니다. 이 값은 McKinsey의 개인화 매출(revenue) lift
  리서치(평균 10~15%, 기업별 5~25% — [The value of getting personalization
  right—or wrong—is multiplying](https://www.mckinsey.com/capabilities/growth-marketing-and-sales/our-insights/the-value-of-getting-personalization-right-or-wrong-is-multiplying))를
  참고한 보수적 가정입니다. 참고로 Salesforce가 2017년 1.5억 건의 쇼핑 세션을
  분석해 보고한 수치([Study: Personalized Recommendations Produce 4 Times More
  Conversions](https://www.practicalecommerce.com/study-personalized-recommendations-produce-4-times-conversions))는
  개인화 추천 노출 시 전환율이 최대 4.6배, 장바구니 담기율이 +24% 높다는 훨씬
  공격적인 값인데, 벤더 자체 조사라 선택편향 가능성이 있어 채택하지 않았습니다.
  (이전 버전 문서에는 "McKinsey, Salesforce 등에서 흔히 인용되는 10~30% 범위"라고
  적혀 있었으나, 이는 서로 다른 지표—마케팅 ROI, 매출, 전환율—를 부정확하게
  뭉뚱그린 표현이라 위와 같이 정정합니다.)
- 적용 범위: 실제로 개인화(매치 점수·비교 근거 노출)가 작동하는 경로, 즉 **A그룹의
  '추천' 진입 세션에만** 조회->장바구니, 장바구니->구매 확률에 +15%를 곱함. 검색/GNB
  진입이나 B그룹은 Kaggle 실측값을 그대로 사용 — 이 경로들은 우리 앱에서 매치스코어/
  비교 기능이 노출되지 않기 때문입니다.
- Kaggle 대응물이 없는 나머지 지표(NPS, 반응입력률, N일 재구매율, 비교기능 사용률 등)도
  전부 이 **동일한 +15%** 하나만 사용해 A값을 산출했습니다(좋을수록 좋은 지표는 x1.15,
  낮을수록 좋은 지표(체류시간의 반대 개념인 결정 소요일수, NPS 비추천 비율)는 /1.15).
  이는 "Kaggle 실측"이 아니라 **명시적 가정**입니다. 정확한 계수는 `scripts_v2/02_simulate_events.py`의
  `LIFT`, `KAGGLE_VIEW_TO_CART`, `KAGGLE_CART_TO_PURCHASE`, `BASE_B` 를 참고하세요.

## 상품 카탈로그 확장 (사내 반려동물 상품 분류 체계 반영)

v1의 `products_master.csv`는 5개 대분류 x 12개 상품(총 60개)의 단순 구조였습니다.
v2는 사내에서 정리한 반려동물 상품 분류 체계 참조표(카테고리/서브카테고리, 건강기능
코드, 원재료/알레르겐 코드, 영양성분 참조 코드)를 반영해 아래 3개 파일로 정규화했습니다.
이 구성비 자체는 Kaggle과 비교할 대상이 아닌 카탈로그 설계 값(가정)입니다.

- **products_master.csv** (91개 상품): `category_code`(FOOD/SUPPLEMENT/TREAT/GOODS),
  `subcategory_code`(예: DRY_FOOD, CHEWABLE_SUPPLEMENT, JERKY_TREAT 등 26종),
  `species`(값은 `dog`/`cat`/`dog/cat` 세 가지 — "모든 종에 적용 가능"은 `"both"`가
  아니라 `"dog/cat"`으로 저장됩니다. 이 표기 차이 때문에 실제로 발생했던 버그는
  아래 "v0.3 파이프라인 버그 수정" 절 참고), `function_code`(GENERAL 포함 17종 건강기능),
  `price_krw`, `allergen_groups`(해당 상품이 포함한 알레르겐 그룹, 콤마 구분)
- **products_ingredients.csv** (long format): 상품별 원재료 코드·알레르겐 그룹.
  독성 성분(마늘/양파/자일리톨/포도 등)은 실제 상품에 쓰이지 않으므로 카탈로그
  생성에서 제외했고, 유저 알레르기 배제 로직에서만 참조 가능한 원재료만 사용했습니다.
- **products_nutrients.csv** (long format): 상품별 영양성분 코드·단위·값. 사료/간식은
  서브카테고리별 일반영양성분(조단백/조지방/수분/조섬유/열량) 범위에서, 영양제는
  건강기능코드에 연계된 활성성분(예: JOINT->글루코사민/콘드로이틴, GUT->프로바이오틱스)
  범위에서 샘플링했습니다.

`users_master.csv`도 `pet_has_allergy`(Boolean)를 `pet_allergy_group`(알레르겐 그룹
코드, 없으면 공백)으로, 신규로 `pet_care_need`(관심 건강기능 코드, 없으면 공백)를
추가했습니다. 두 필드의 보유율(22%/35%)은 반려동물 알레르기 유병률·건강 관심사 비율에
대응하는 Kaggle 데이터셋이 없어 검증할 수 없으므로, v1의 알레르기 보유율(22%)을 그대로
승계한 가정입니다.

이 확장된 카탈로그는 이벤트 시뮬레이션의 개인화 로직에도 반영됩니다: **A그룹의 '추천'
진입 세션에서만** 유저 반려동물의 알레르겐을 포함한 상품을 배제하고, 관심 건강기능이
있으면 해당 기능 상품을 우선 노출합니다. 그 외 경로(검색/GNB, 또는 B그룹)는 무작위
상품을 노출해 "개인화 미노출" 상태를 재현합니다.

## funnel_step / trigger_type 컬럼

데이터 수집 계획서 v0.1의 "퍼널 이벤트" 시트 정의를 반영해 `events_log.csv`에 두 컬럼을
추가했습니다.

- `funnel_step`: 가설1(구매 여정) 매핑만 전체 이벤트에 적용
  (진입 / 상품탐색 / 장바구니담기 / 이탈 / 이탈(장바구니) / 구매완료), 그리고 가설3
  (반응입력 여정) 매핑(알람노출/알람확인/입력시작/입력완료(유효|무효)/입력중이탈/재진입).
  가설2(추천재구매 여정) funnel_step은 계획서상 별도 매핑이 정의돼 있으나, 한 이벤트
  행이 여러 가설의 퍼널 단계를 동시에 값으로 가질 수 없어 이 컬럼에는 넣지 않았습니다 —
  `scripts_v2/04_funnel_cohort_analysis.py`가 v1과 동일하게 `event_type` + `source`
  필터링으로 가설2 퍼널을 직접 계산합니다.
- `trigger_type`: 계획서 정의대로 트리거 기반 이벤트에만 채웁니다
  (`nps_popup_impression` -> `purchase_confirm_d3`, `reaction_require_alarm` ->
  `delivery_status_complete_d0`).

## v0.4 표본 확대 (검정력 확보)

유의(p<0.05)해졌습니다 — v0.2/v0.3 대비 이벤트/주문 총량이 다시 크게 늘어난

**Kaggle 샘플링 방식의 한계**
1. 참고한 Kaggle 데이터셋은 범용 이커머스(멀티카테고리 쇼핑몰, 화장품, 리테일) 로그이지,
   '골라주개냥'처럼 AI 반려동물 맞춤형 + D2C + 초기 단계 스타트업 서비스의 데이터셋은
   아닙니다. 반려동물 카테고리 특유의 구매 패턴(재구매 주기, 브랜드 충성도 등)까지는
   반영하지 못한다는 한계가 있으며, 실제 서비스가 출시되어 자체 데이터가 쌓이면 그
   데이터로 다시 보정할 계획입니다.
2. Kaggle 원본 로그는 월별 5~9GB에 달하는 대용량이라 전체를 담을 수 없어, 월별 5만 행
   단위로 행 무작위 샘플링을 진행했습니다. 이 방식은 이벤트 타입 간 비율(조회 대비
   장바구니 건수 등)을 추정하는 데는 유효하지만, 한 유저의 세션을 처음부터 끝까지
   연속으로 담고 있지는 않습니다.
3. 이 때문에 Kaggle로는 확인할 수 없었던 상품 상세 체류시간, 구매결정 소요시간, N일
   재구매 타이밍은 계획서에 명시된 추정치를 그대로 사용했습니다.

**A/B 처치 효과(+15%)는 실측이 아니라 가정**
- 우리 서비스의 핵심 가설(맞춤 추천이 전환을 높인다)은 Kaggle 어디에도 대응하는 실험
  데이터가 없는, 우리만의 검증되지 않은 가설입니다. 자세한 근거와 정정 내역은 위
  "A/B 처치 효과 가정 (LIFT = +15%)" 절을 참고하세요.
- 이 +15% 하나의 계수를 NPS·반응입력률·N일 재구매율·비교기능 사용률 등 Kaggle에
  대응물이 없는 모든 지표에 동일하게 적용했습니다 — 지표마다 임의로 다른 격차를 만들지
  않기 위함이지만, "이 지표들이 실제로도 정확히 15%씩 개선된다"는 실증적 근거는
  없습니다.

**시뮬레이션 설계상의 인위적 단순화**
- 반응입력 퍼널에서 "알람 확인"과 "입력 시작" 이벤트가 코드상 항상 함께 발생하도록
  짜여 있어, 이 구간 전환율이 항상 100%로 고정됩니다. **v0.4에서 새 이탈 확률을
  추가할지 검토했지만 유지하기로 결정했습니다** — 반응 입력 자체가 버튼 하나를
  누르고 등록하기를 누르는 가벼운 동작이라 "확인했는데 시작을 안 하는" 이탈은
  실제로 거의 없을 가능성이 높고, 진짜 마찰 지점(푸시 알림을 보고 화면에 들어오는지
  여부, 즉 "알람확인")은 이미 확률이 걸려 모델링돼 있기 때문입니다. 즉 이 항목은
  데이터 한계가 아니라 검토를 거친 의도된 설계입니다.
- 상품 카탈로그(91개 상품의 카테고리/기능 분포)와 유저의 알레르기 보유율(22%)·건강관심사
  보유율(35%)은 Kaggle이나 다른 실측 데이터로 검증할 수 없는, 팀이 설계 시점에 정한
  가정값입니다.
