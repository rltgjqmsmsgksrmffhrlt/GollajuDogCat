# 인증/인가 관련 초기 방향 설정

- (인증 방식) JWT + 게이트웨이 단일 검증
    - 게이트웨이만 JWT 서명 검증을 하고, 다운스트림은 게이트웨이가 전달하는 헤더를 신뢰하는 구조
    
- (토큰)
    - access/refresh 토큰 분리, 각각 TTL(1시간/7일)
    - 로그아웃 시 블랙리스트 처리 방식
    - 토큰 관련 정보를 rdb에 저장하지 않고 인증 도메인의 redis에만 저장
    로그아웃을 하면 블랙리스트에 등록하고, access token의 만료시간만큼 TTL을 걸어 자동 접근 차단
    - 게이트웨이에서는 인증 도메인에게 블랙리스트 여부 boolean값을 조회해 요청 차단/수용
    - 토큰 서명 방식: RSA + JWKS 기반으로 구현( 비대칭키로 서명하고, 공개키는 JWKS 엔드포인트로 노출해 게이트웨이가 검증에 사용)
    
- 다운스트림 내 신뢰 모델
    - 게이트웨이에서 인증이 된 요청인지 구분하기 위해 헤더에 시크릿값을 넣어주었음
    - 시크릿 값을 각 서비스들이 미리 저장한 뒤 요청이 왔을 때 시크릿값 확인.
    - 시크릿값이 다르거나 확인이 되지 않는다면 차단
    
    개선 방향: RSA + JWKS 기반으로 전환.
    
    - 배경: 정적 시크릿은 한 번 유출되면 만료 없이 영구적으로 신원 위조에 악용될 수 있다는 약점이 있음
    - 방식: 게이트웨이가 요청마다 짧은 TTL(30초~1분)의 내부 전용 토큰을 RS256으로 서명해 헤더에 실어 보내고, 각 서비스는 게이트웨이 공개키로 서명만 검증
    - 이점: 서비스가 비밀 값을 들고 있을 필요가 없어지고, 유출돼도 짧은 시간 내 만료되며 개인키 없이는 새로 위조 불가능
