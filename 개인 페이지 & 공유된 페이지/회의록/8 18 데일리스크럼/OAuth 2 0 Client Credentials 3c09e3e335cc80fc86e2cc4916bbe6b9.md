# OAuth 2.0 Client Credentials

|  | Client Credentials | mTLS |
| --- | --- | --- |
| 확인 방법 | 토큰(문자열)으로 신원 증명 | 인증서(암호화 키 쌍)로 신원 증명 |
| 구현 위치 | **애플리케이션 코드**(Spring Security 필터 등) | **인프라 레벨**(서비스 메시, Istio) |
| 구현 난이도 | 상대적으로 낮음 | 인증서 발급/자동 회전 인프라 필요 |
| 구현 가능 여부 | Spring Security로 직접 짤 수 있음 | 인프라팀 세팅이 선행되어야 함 |

## 백엔드 인증/토큰 방식 비교

| 항목 | OAuth 2.0 Client Credentials | 공유 시크릿 헤더 |
| --- | --- | --- |
| 개념 | 매 요청 전, 인증 서버에서 단명(short-lived) 토큰을 발급받아 사용 | 고정된 비밀값을 헤더에 실어 매번 동일하게 전송 |
| 유효기간 | **짧음(예: 1시간), 만료 시 자동 무효화** | 없음 — 직접 교체하기 전까지 영구 |
| 유출 시 리스크 | **낮음(만료로 자동 제한)** | 높음 — 교체 전까지 계속 악용 가능 |
| 구현 주체 | **백엔드** (토큰 발급/검증 로직을 애플리케이션 코드로 구현) | 백엔드 (구현은 가장 간단) |
| 필요 인프라 | 별도 인증 서버(또는 Spring Authorization Server) | 없음 |
| 권한 세분화 | **가능**(스코프 기반으로 서비스별 권한 구분) | 불가(시크릿 하나로 전체 허용) |
| 2개월·신입 팀 규모 적합성 | **높음**(Spring Security 기반 지식 재사용 가능) | 높음(단, 보안 수준 낮음) |

### OAuth 2.0 Client Credentials

- **적용 범위**: 백엔드 서비스 간 통신 전체(member/subscription/payment/notification/timedeal-service), 백엔드↔AI 서버 통신
- **담당**: 백엔드 (인증 서버 구성 및 각 서비스의 토큰 발급/검증 로직 구현)
- **선정 이유**:
    1. mTLS는 서비스 메시 인프라 구축이 선행되어야 하나, 2개월 일정과 인프라팀의 병행 과업(EKS/ECS, CI/CD 등)을 고려하면 우선순위에서 밀릴 가능성이 큼
    2. OAuth Client Credentials는 애플리케이션 레벨에서 백엔드가 자체적으로 구현 가능해, 인프라 세팅을 기다리지 않고 즉시 착수 가능
    3. 팀이 이미 사용자 인증에 Spring Security·JWT를 채택하기로 했으므로, 동일한 기술 스택의 연장선에서 학습·구현 부담이 적음
    4. 토큰의 단명(short-lived) 특성상 공유 시크릿 방식보다 보안 수준이 높음

즉시 응답이 필요 없는 통신(결제완료→알림, 구독취소→결제환불 등)은 이 인증 흐름 대신 Kafka 이벤트 발행/구독으로 처리
