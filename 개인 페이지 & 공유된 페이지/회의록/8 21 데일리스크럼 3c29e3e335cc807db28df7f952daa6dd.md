    - 우선순위 재검토 필요한 부분
        - **자연어 검색 기반 추천(2.1.5-5)**: 이건 사실상 AI/LLM 영역입니다. 백엔드가 "구현"하는 게 아니라 AI 서버에 요청을 위임하고 응답을 매핑하는 정도인데, 문서에는 이 경계가 안 나와 있습니다. **짧은 개발 기간에는 MVP에서 제외하거나 AI팀 리소스 확정 후 재논의를 제안**합니다.
        - **영수증 OCR 분석(2.1.4-2)**: OCR은 AI팀 또는 외부 API(Naver Clova OCR 등) 의존이 필수입니다. 백엔드가 자체 구현할 영역이 아니므로, "S3 업로드 API + AI 결과 수신 API" 정도로 축소하는 게 현실적입니다.
        - **사진 기반 프로필 자동입력(2.1.1-1)**: Vision AI 필요 + 정확도 검증 이슈가 커서, 짧은 기간에는 우선순위를 낮추는 게 맞다고 봅니다.
        - **성분 자동 비교/점수화(2.1.5-3)**: "맞춤형 점수"를 계산하는 로직이 규칙 기반인지 ML 기반인지에 따라 완전히 다른 프로젝트가 됩니다. 규칙 기반이라면 백엔드가 할 수 있지만, 신뢰도 있는 점수 산출 기준(가중치, 데이터 출처)을 PM/AI팀과 먼저 정의해야 하며, 정의 없이 시작하면 일정 리스크가 큽니다.
    - 타 직군에 요청/확인해야 할 사항
        
        #### PM팀에게
        
        - B2C vs B2B(D2C) 여부: 이건 서비스의 근본 구조(사용자 인증 방식, 데이터 모델)를 결정하므로 최우선으로 확인. 현재 문서는 "보호자(반려동물 주인)"를 대상으로 한 B2C 커머스로 보이는데, PRD에 명시가 안 되어 있다면 이건 팀 전체가 서로 다른 가정을 하고 있을 위험이 큽니다.
        - 상품 데이터의 출처(자체 등록 vs 크롤링 vs 제휴 API)와 소유권/갱신 주기
        - MVP 범위와 정식 우선순위표 (문서의 페인포인트 순위표는 "문제"의 우선순위이지 "기능"의 우선순위가 아님 — 이 갭을 PM에게 명확히 확인 필요)
        - 진료내역 데이터 수집 여부와 법적 근거(개인정보보호법상 민감정보 해당 가능성 — 문서에도 `확인필요(보안)`라고 이미 표시되어 있음)
        - 실제 결제(PG 연동)를 구현하는지, 모의결제로 대체하는지
        
        #### AI팀에게
        
        - 리뷰 요약, 성분 점수화, 추천, OCR 각각을 AI팀이 담당하는지 ****명확한 역할 분담
        - AI 응답을 어떤 형태(동기 REST / 비동기 이벤트 / 배치)로 백엔드에 전달할지
            - 백엔드 아키텍처(큐 도입 여부 등)에 직접 영향
        - 요청/응답 API 스펙(초안이라도)과 예상 응답 지연 시간(latency)
            - 알림/추천 API의 타임아웃 설계에 필요
        
        #### 프론트엔드팀에게
        
        - "뎁스 간략화 UX"에서 요구하는 화면별 필요 데이터
            - (한 번의 API 호출로 묶어야 하는 범위 확인 — BFF 패턴 필요 여부 판단)
        - 다중 반려동물 프로필 전환 시 화면 상태 관리 방식
            - (백엔드가 세션/컨텍스트를 어떻게 유지해야 하는지)
        
        #### 인프라팀에게
        
        - S3 저장 방식: presigned URL로 프론트/AI가 직접 업로드하는 구조인지, 백엔드가 중계 API를 만들어야 하는지
        - 알림 발송 인프라 (FCM, AWS SES/SNS 등) 확정 여부
        
        #### 필요한 공유 페이지 제안
        
        - API 명세서 (Swagger/OpenAPI)
            - 프론트/AI와의 계약(contract) 정의용, 개발 초기부터 필수
        - ERD/도메인 모델 문서
            - 특히 반려동물-프로필-리뷰-구매이력 연관관계는 복잡하므로 팀 전체가 봐야 함
        - 용어사전: "프로필", "적합성", "관찰중" 등 문서에 자주 쓰이는 용어의 정의가 코드/DB 스키마와 어긋나지 않도록 필요하다.
    - 백엔드 관점 기타 주의사항
        - **데이터 정합성**: 주문-피드백-알림처럼 여러 도메인에 걸친 이벤트가 많으므로, MSA로 갈 경우 이벤트 기반 아키텍처(Kafka/RabbitMQ)와 최종 일관성(eventual consistency) 설계를 초반에 정해둬야 합니다. 이걸 나중에 추가하면 리팩토링 비용이 큽니다.
        - **AI 연동 지점의 장애 격리**: 추천/리뷰요약/OCR 등 AI 의존 기능이 많은데, AI 서버 응답 지연이나 장애가 전체 서비스에 전파되지 않도록 Circuit Breaker(Resilience4j) 같은 패턴을 초반부터 고려하는 게 좋습니다.
        - **민감정보 처리**: 진료내역이 실제로 수집된다면 Spring Security + 암호화(필드 레벨 암호화 등) 설계가 필요하고, 이는 일정에 별도로 반영해야 합니다.
        - **알림 스케줄링**: 7/14/30일 후 발송은 단순 스케줄러(@Scheduled)로는 사용자별 개별 트리거 관리가 어려우니, Quartz나 메시지 큐 기반 지연 발송을 검토하는 게 낫습니다.

    ### 2.1.1 프로필

            → 사진은 S3에 저장하면 될 것 같은데 진료내역도 사진인지 텍스트인지?
            → 진료내역 암호화를 한다면 양방향 암호화 필요
            
    2. 반려동물에게 맞는 상품 기준 정보 제시 
        1. 먼저 확인해야 할 정보 제시, 상품을 고를 때 기준이 되는 정보로 수정
    3. 반려동물 생애주기에 맞춰 상품 정보나 필요한 부분 제시
    → 생애주기 판단 자체는 AI가 계산하는 걸까요? 
    4. 반려동물 프로필 추가 
        1. 여러 마리를 각각 등록하고 따로 쇼핑하기
        → 주인:반려동물 = 1:n
        1. 대표 반려동물을 저장해두고, 변경이 필요할 때 마이페이지에서 반려동물 변경
        2. 로그인을 할 때마다 어느 반려동물을 두고 쇼핑할건지 고르게 하기
        2. 프로필을 바꾸면 추천, 리뷰, 구매내역도 각각 다르게?  
            1. 리뷰 남기면 해당 프로필의 품종, 나이, 질환 등을 같이 표시 = 리뷰에 반려동물 프로필 자동으로 붙이기
            → 리뷰에서 반려동물 API 호출
            2. 사료를 샀을 때 같이 먹는다면? 누가 먹나요? (누가 먹는지 구입을 했을 때 선택할 수 있게(복수 선택 가능))
            → 주문상품:반려동물=N:M 
    
    ### 2.1.2 리뷰 분석 & 리뷰 필터
    
    1. 리뷰 필터: 유저의 반려동물과 같은, 비슷한 타유저의 리뷰를 조회할 수 있도록 필터 제시 (EX) 화해 앱)
    → 반려동물정보 API 호출. 
    2. 리뷰 요약: 
        1. 긴 리뷰를 긍정적인 부분/아쉬운 부분 나누어서 요약
        2. 기호성, 변, 피부, 체중 등을 반응 별로 후기를 정리하여 유저를 전부 읽지 않아도 핵심 요약
        → 요약한 내용은 리뷰 목록 조회할 때마다 새로 계산 아니면 한 번 계산해서 어딘가에 저장. 후자일 것 같긴하네요. 그럼 주기를 얼만큼..
        1. 리뷰 작성 시점마다
        2. 일정 주기 - 배치처리 해본적이 없어 개인적으로 도움이 될 것 같다(노여진)
        → AI 파트에게 데이터 전달하면 리뷰 요약을 진행하고 다시 백엔드로 전달해서 DB에 저장
        3. 일정 개수마다 
    3. 신뢰 가능한 정보/리뷰 표시 
        1.  몇 번째 구매하는지(구매횟수), 얼마나 오래 썼는지(사용기간) 프로필과 함께 표시
        → 구매횟수는 주문에 API 호출 
        → 사용기간은 어떤 걸 기준으로 계산하는지.
        1. 구매일로부터 지금까지
        2. 사용자가 직접 입력

    1. 뎁스 간략화 → UX
        1. 개인화 추천-바로 결제 (결제의 뎁스 줄이기)
        2. 앱 진입 후 상단, 바텀 시트 등으로 정보 입력할 수 있도록 (정보 입력 뎁스 줄이기)
    
    ## 2.2 플로우 초안
    
    기본 가정: 앱, 회원가입 해야하는 초기 유저.
    
    1. 회원가입 (SNS 회원가입 - `카카오 / 네이버/ 구글 프론트&백 상의필요`)
    2. 로그인 
    3. 반려 동물 프로필 등록  (기능: `2.1.1 프로필, 2.1.6 뎁스 간략회 UX`)
    4. 홈 화면 진입
        1. 홈 화면 진입 시 어떤 아이 위주로 상품을 살펴 볼지 프로필 선택
        2. 반려 동물 프로필 및 생애주기에 맞는 상품 정보 추천 (기능: `2.1.3 상품 추천`) 
        3. 상품 상세 페이지 
            1. 성분 확인 (기능: `2.1.5 성분 분석, 비교 및 해석`)
            2. 리뷰 확인 (기능:  `2.1.2 리뷰 분석 / 리뷰 요약 / 리뷰 신뢰도 표시` )
        4. 상품 구매 페이지 (기능: `2.1.6 뎁스 간략화 UX`)
        5. 상품 결제
        6. 상품 배송 (배송 취소/배송 위치 등)
        7. 상품 수령  (교환/환불/문의 등)
    5. 상품 구입 이후 피드백 (기능: `2.1.4 제품 구입 이후 체크`)
    6. 피드백을 다음 상품 선택 또는 재구매에 반영
    
    예외 케이스
    
    - 반려 동물 프로필과 맞는 리뷰가 없는 경우
    - 반려 동물 프로필과 맞는 상품이 없는 경우
        - 체험단 → 비슷한 종이나 생애주기/ 몸무게 등을 가진 경우
    - 콜드 스타터 유저-상품 구입 이후 피드백 데이터가 없는 경우
        - 기본 프로필 정보로만 상품 추천

        - 각 기능별 필수 데이터, 주의 사항, 권한 등이 있다면 정리 필요, 우선순위 판단 필요
        - 수정 및 삭제는 우선순위 후순위(사용자 플로우 우선), 이커머스 필수 기능 외 부가 기능 후순위로

            - 상품 종류마다 비교 기준을 다르게 보여줄 때, 종류마다 가지고 있는 비교 기준은 무엇인지
        - 용어 맞춤 필요: 상품 카테고리 vs 상품 종류 등등
    - **상품 관련 필요 사항**
        - B2C/상품 관리 방법
            - **상품 등록 플로우** (상점이 먼저 입점하는 과정, 필수 입력 데이터 등)
                - 등록에 카테고리 지정이 필요하다면 카테고리 조회 API가 플로우에 포함
            - 상품 등록에 필수로 포함되어야하는 내용 정의 필요
                - 필수로 포함되어야 하는 내용을 등록 페이지에서 확인하기 위해 API 포함
        - 상품 추천 외에 기본적으로 상품 목록을 조회하는 페이지가 있는지
            - **상품 추천 외의 상품 조회 플로우** (목록을 조회한다면 관련 필터링, 정렬 조건 등)
                - 필터링과 정렬이 사용된다면 관련 조건 조회 API 필요, 조건 데이터 정의 필요
    - **상품 분석 관련 필요 사항**
        - 어떤 플로우를 통해 상품을 분석하고 비교하는지, 관련 기능(API)이 무엇인지 파악 필요
            - 어떤 API를 호출해서 어떤 데이터가 나오는건지 파악 필요함
            - 전체적으로 AI 업무로 예상됨: 언제 어떤 정보를 기반으로 호출하고 뭘 보여야 할지 정확히 필요 → 화면 정의서가 있으면 좋을 것 같기도 하네요
        - 주요 성분에 대한 표, 급여 가이드 등은 정적으로 관리되는게 맞는지
    - **주문 및 결제 관련 필요 사항**
