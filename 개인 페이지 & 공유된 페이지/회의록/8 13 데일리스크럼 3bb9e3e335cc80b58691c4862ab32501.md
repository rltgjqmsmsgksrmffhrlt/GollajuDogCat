    ### 기획/설계가 아직 안 나온 상황에서 할 수 있는 것

        - **결제**는 방향(PG 사용 vs 자체 구축)에 따라 갈리지만, PG를 쓰기로 하면 그 부분을 미리 혼자 연습해보는 것도 좋다고 하심
    
    ### 2. 폭포수 vs 애자일 — 진행 방식 문제 제기
    
    - 지금 팀은 "기획 다 끝나야 설계 시작"하는 폭포수 방식으로 가는 듯한데, 이러면 **뒷사람(백엔드 등)이 계속 기다려야 하는 병목**이 생김
    - 강사님 본인 팀은 애자일로 끌고 가는 예시를 보여주며 대안 제시:
        - 디자이너가 부족하면, **기획자 없이 백엔드+프론트가 직접 "러프한 기능 명세"**를 작성 (도메인별 대/중분류로 간단히)
        - 정식 와이어프레임 없이도 **대충 그린 유저플로우**만으로 시작 가능
        - **핵심 기능 하나를 먼저 선정해서 그것부터 개발** → 검증되면 다른 기능을 점진적으로 붙여나가는 방식 추천
    - 이런 식으로 "와이어프레임이라도 러프하게 있어야 ERD 설계가 가능하다"는 걸 팀(PM 등)에 건의해보라고 조언
    - **개발 기간이 2~3주밖에 안 되는데 기능이 7개 이상이면 백엔드가 부담스러워질 것**이라고 미리 경고 — 이 부분도 팀에 얘기해보길 권함
    
    ### 3. AI 연동 시 DB 관리 주체
    
    - AI가 RAG를 구축한다면 **벡터 DB**가 필요한데, PostgreSQL이 벡터 검색(코사인 유사도 등)을 지원하는 확장 기능이 있어서, **같이 쓰면 Postgres 하나로 관리 가능** (배포는 인프라팀 담당)
    - 규모가 커지면 나중에 분리할 수도 있음 — MSA 업그레이드하듯 점진적으로
    - 만약 AI가 별도 벡터DB(Pinecone 등)나 Redis Search 같은 걸 쓰게 되면, 이건 **백엔드 혼자 정할 게 아니라 인프라+AI+백엔드가 함께 조율**해야 함
    - **결정 순서**: AI팀이 조사 후 "이런 기능이 필요하다"고 제안 → 백엔드와 AI가 "같이 쓸지 따로 둘지" 논의 → 인프라팀이 그에 맞게 배포 설정(Docker 이미지 버전 등)을 조정. 백엔드/AI의 코드(JPA 등) 자체는 크게 안 바뀜
    
    ### 4. 배송/재고 도메인 설계
    
    - 쿠팡처럼 직접 배송 시스템을 관리하는 방향이면 지금 할 수 있는 게 없음
    - 택배사 API를 쓰는 방향이면 그런 대로 가능하지만, **강사님은 배송 자체를 깊게 만들지 말라고 추천** — 가볍게 CRUD 수준으로만
    - **배송 도메인을 독립 서비스로 분리하는 건 규모가 과함** → 배송지 정보는 **회원(Member) 애그리거트에 포함**시키고, 결제 등에서 필요할 때 회원 API를 호출해서 가져오는 방식이 제일 심플하다고 조언 (이전에 저희가 얘기했던 모듈 간 서비스 인터페이스 호출 방식과 같은 원리)
    
    ### 5. 남는 시간(9월 10일~10월 말)에 뭘 할지 — 딥다이브 추천
    
    - 개발은 9월 초·중순에 끝나고, 이후 10월 말까지는 버그 수정 외엔 할 게 마땅치 않은 일정
    - **정답은 없지만 강사님 추천**:
        - **모놀리식으로 간다면** → 각 기능을 더 깊게 파고들기(딥다이브)
        - **MSA로 간다면** → 성능 테스트, 인프라 환경, 서비스 간 예외/장애 처리에 집중
        - 결국 하나(메인 기능)를 딥다이브하면 예외처리·장애처리가 자연스럽게 따라오게 됨
        - *협업 경험은 "당연히 가져가는 디폴트"**이지 특별한 차별점으로 보지 않음 — 이 부분은 굳이 집중 안 해도 됨
        - 강사님 팀은 **성능 테스트 + 모니터링**을 제일 추천 — 가장 빠른 피드백 루프(왜 안 되는지, 왜 예외 터지는지)를 준다고 함. 안 쓰는 시간엔 인프라(Terraform)를 꺼뒀다 켰다 하며 비용 절감
