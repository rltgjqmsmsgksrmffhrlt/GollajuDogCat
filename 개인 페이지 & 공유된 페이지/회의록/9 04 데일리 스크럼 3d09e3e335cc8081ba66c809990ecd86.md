### 피드백 정리

- behavior_events 테이블 관련 요약
    - 결론: 백엔드가 단순 적재만 하고 활용은 안 한다면, 프론트가 AI(FastAPI) 서버로 바로 쏘는 게 맞음
    - MSA라면 프론트 → API 게이트웨이(인증/인가) → 곧바로 FastAPI로 전달하면 되고, 스프링(백엔드)이 중간에서 처리할 로직이 없으면 굳이 거칠 필요가 없음
    - DB 소유권보다는 역할 분리의 문제 — API 서버가 그쪽 DB에 직접 접근 못 하게 정책으로 막으면, "모든 AI 데이터는 FastAPI를 거쳐야 한다"는 정책이 자연히 생기는 것
- 장바구니 관리 Redis 방식 요약
    - 데이터가 많이 쌓이면(억 단위) 메모리 부담 커져서 장기적으로는 비추천
    - "즉시 삭제하는 정책"이면 Redis만으로도 괜찮음 — 정책에 따라 갈림
    - TTL 자동 삭제(Redis 부하↑) vs RDB 배치 삭제, 둘 다 트레이드오프
    - 표준은 Redis(캐싱) + RDB(백업) 병행
- 추후 관점에서는 좋진 않은데 정책에 따라 다르긴 함. 레디스 vs RDB 트레이드오프가 있다.
    - 서비스상에서 레디스를 많이 사용할수도 잇는데 ttl까지하면 너무 일이 많아진다.
    - 레디스만 고집하는건 좀 그렇고 RDB 같이 사용하는 방법도 있다. (Redis 캐싱 + RDB 백업)
- 공통으로 참조하는 값:
    - Enum으로 관리하는게 좋을 것 같다.
    - 데이터가 급격히 바뀌는 게 아니라 추가/수정 수준이라 결합도가 크게 안 늘어남
- ERD 1: 리뷰 도메인에 있으면 될 것 같다.
- ERD 2: 원료 코드가 재고로 따로 관리가 필요하지 않다면 배열로 관리해도 무방할 것 같다.
