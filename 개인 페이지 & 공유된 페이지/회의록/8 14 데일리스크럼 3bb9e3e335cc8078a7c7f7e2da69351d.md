- 백엔드 프로젝트(빵빠레 팀) 구조 정리
    
    클라우드 구성: 서비스별 EC2 + Docker
    
    네트워크: 게이트웨이는 public, 서비스는 private + SG로 제한
    
    서비스마다 독립 DB, 독립 배포(EC2), 유레카로 서비스 디스커버리, 게이트웨이가 유일한 진입점
    
    CI/CD 관련 yml 파일
    
    https://github.com/KT-Cloud-2-BDS/bds_backend/tree/develop/.github/workflows
    
    ```java
    1. 코드 push/PR (해당 서비스 디렉토리 변경 감지)
    ↓
    2. CI (ci-<service>.yml) — 빌드·테스트·커버리지 검사
    ↓ 성공 시
    3. CD 트리거 (cd-services.yml / cd-platform.yml)
    ↓ 서비스 이름 추출 후 위임
    4. cd-common.yml — 전 서비스 공용 배포 로직
    ↓
    5. EC2에서 실제 컨테이너 교체
    ```
    
    ### 1.  CI
    
    - **트리거 조건**: `services/<service-name>/**` 등 해당 서비스 경로가 변경될 때만 실행 (서비스 무관한 변경에 불필요한 CI가 도는 것을 방지)
    - **체크아웃 최적화**: `actions/checkout@v4` + sparse-checkout으로 변경된 서비스와 공통 모듈만 받아 빌드 시간 단축
    - **빌드/검증**: `./gradlew :services:<service>:build` — 빌드 + 테스트 + Jacoco 커버리지 체크(기준치 예: 80%)
    - **산출물 보관**: 통과 시 생성된 fat JAR을 GitHub Actions artifact로 업로드 (CD 단계에서 재사용)
    
    ### 2. CD 트리거
    
    - `cd-services.yml`이 `workflow_run`으로 대응하는 CI 워크플로우(`CI - <service>`)의 완료 이벤트를 구독
    - 워크플로우 이름에서 서비스 이름을 파싱해 `cd-common.yml`에 위임
    - `cd-platform.yml`(게이트웨이·디스커버리 등 플랫폼 서비스)은 배포 순서 의존성이 있음: **discovery-service를 gateway-service보다 먼저 배포**해야 함 (게이트웨이가 기동 시 서비스 디스커버리에 등록을 시도하므로, 디스커버리가 먼저 살아있어야 함)
    
    ### 3.  cd-common.yml — 공통 배포 로직
    
    1. **JAR 재사용**: CI에서 테스트까지 통과한 JAR을 그대로 다운로드(`download-artifact`, CI 실행 run-id 참조)해 사용. 재빌드하지 않음으로써 "테스트 통과 결과물 = 배포되는 결과물"을 보장
    2. **AWS 인증**: 정적 액세스키 대신 **OIDC 기반 role-to-assume** 사용 — 장기 노출되는 인증정보 없이 임시 자격증명으로 인증
    3. **Docker 이미지 빌드·푸시**: 이미지 태그를 커밋 SHA로 지정해 배포 이력과 커밋을 1:1로 추적 가능(롤백 시에도 활용)
    4. **SSM Run Command로 EC2 배포**: `Service=<이름>` 태그가 붙은 대상 EC2에 배포 명령 전송. EC2 내 실행 스크립트가 다음을 수행:
        - **IMDSv2로 EC2 프라이빗 IP 조회**: 컨테이너 내부에서 알 수 없는 EC2의 실제 IP를 `169.254.169.254` 메타데이터 엔드포인트로 조회해 컨테이너 환경변수(예: `EUREKA_INSTANCE_IP_ADDRESS`)로 주입
        - **Parameter Store에서 설정값 조회**: 공유 설정(`/shared/env`)과 서비스별 설정(`/services/<service>/env`)을 병합해 임시 env 파일 생성
        - **컨테이너 교체**: 기존 컨테이너 종료 후 신규 이미지로 교체, env 파일은 주입 직후 즉시 삭제(디스크에 시크릿 잔존 방지)
        - **헬스체크**: `/actuator/health`를 최대 30회(총 150초) 재시도 폴링, 실패 시 배포 실패 처리
    5. **롤링 배포**: `-max-concurrency 1`(한 대씩 순차 교체), `-max-errors 0`(하나라도 실패 시 즉시 중단)으로 다운타임 최소화
    6. **배포 완료 대기**: 워크플로우가 SSM 명령 상태를 10초 간격, 최대 20분(120회) 폴링하여 전체 인스턴스 배포 완료 확인

### 피드백

***해당 질문-피드백은 AI, 인프라와의 팀 미팅 전에 이루어짐**

- 멀티 모듈 구조는 왼쪽(빵디즈) 형태가 적합해 보인다. 틀린건 아님.
- config-server, 서비스 디스커버리 모두 k8s를 사용한다면 필요없어지게 된다. 인프라팀과 논의 필요.
- 만약 k8s 사용하지 않는다면 Eureka, config, gateway 등은 먼저 설정하고 시작하는 것이 맞다.
- 스펙 관련해선 인프라가 비용 책정하고 설정하는게 맞다.
    - 최소 기준은 없지만 마이크로 서비스 수에 따라 인스턴스 수가 늘어날 수 있음만 전달되면 될 것 같다.
- yml 관련해선 k8s를 사용한다면 인프라팀에서 pod.yml 구성을 해줄거다.
    - k8s를 사용하지 않는다면, cicd 배우고 싶다면 공부해서 적용해보길 추천한다.
