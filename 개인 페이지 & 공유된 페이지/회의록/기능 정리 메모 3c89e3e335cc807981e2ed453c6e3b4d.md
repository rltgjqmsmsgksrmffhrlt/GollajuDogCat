# 백엔드 서비스별 기능 정리 (IA · 유즈케이스 · AI 스키마 통합)

> 근거 문서: ① IA 문서(화면 단위 정리), ② 유즈케이스 시나리오(회원가입/상품탐색/리뷰/결제/배송/사용후추적/반려동물추가), ③ AI 팀 통합 데이터 스키마 요청서
전제: Spring Boot 4.1 / Java 25, 모노레포 멀티모듈 MSA, K8s(Eureka 미사용), 자사 브랜드몰(마켓플레이스 아님)
권한 표기: `PUBLIC`(비로그인) / `MEMBER`(로그인 회원) / `SYSTEM`(배치·내부 스케줄러) / `EXTERNAL`(외부 시스템 콜백) / `ADMIN`(운영자, **백오피스 미정의 — 4장 참고**)
> 

### **AI 초안이라서 수정 필요 (해당 문서로 확정 아님)**

## 1. 화면 → 서비스 매핑 개요

| 서비스 | IA 문서 상 담당 화면(요약) | 핵심 애그리거트 |

| product-service | 메인(상품리스트·배너·타임딜), 검색, 상품상세, 상품비교, 최근본상품, 재입고알림 | Product, Category, Brand, Inventory, TimeDeal |

| review-service | 상품 리뷰 화면 전체, 마이페이지_리뷰관리, 메인 화면의 "반려동물 상태체크" | Review, PetReactionCheck |

| notification-service | 마이페이지_알림 | NotificationLog, DeviceToken |
| gateway | (화면 아님) 전체 요청 라우팅/인증위임 | - |

## 2. 서비스별 기능 · API(안) · 권한

### 2.1 auth-service

| 기능 | API(안) | 권한 | 근거/비고 |
| --- | --- | --- | --- |
| SNS 로그인(카카오/구글) | `POST /auth/login/{provider}` | PUBLIC | IA_로그인 화면. 이미 가입된 채널이면 바로 메인, 아니면 회원가입 약관 화면으로 |
| 회원가입 | `POST /auth/signup` | PUBLIC | 이름·전화번호·약관동의(필수)·마케팅동의(선택) 포함 |
| 전화번호 인증 | `POST /auth/phone/verify-request`, 
`POST /auth/phone/verify-confirm` | PUBLIC | 외부 SMS/알림톡 벤더 연동 필요(2장 참고) |
| 토큰 재발급/로그아웃 | `POST /auth/token/refresh`, `POST /auth/logout` | MEMBER | - |
| 회원탈퇴 | `DELETE /auth/me` | MEMBER | 성공 시 `MemberWithdrawn` 이벤트 발행 → 각 서비스 cascade |

### 2.2 member-service

| 기능 | API(안) | 권한 | 근거/비고 |
| --- | --- | --- | --- |
| 내 정보 조회/수정 | `GET/PUT /members/me` | MEMBER | 이름·닉네임·전화번호·생일·이메일·**환불계좌** 포함 |
| 배송지 CRUD/기본설정 | `GET/POST/PUT/DELETE /members/me/addresses` | MEMBER | 마이페이지_배송지 관리/추가/수정 |
| 반려동물 프로필 CRUD(다중) | `GET/POST/PUT/DELETE /members/me/pets` | MEMBER | 다견/다묘 지원 (유즈케이스_반려동물 추가) |
| 반려동물 사진 업로드 | `POST /members/me/pets/{petId}/photo` | MEMBER | S3/CDN 외부 연동 |
| 랜덤 닉네임 발급 |  |  |  |

**필드 갭 주의**: AI 스키마의 `pet_profile`은 `birth_date`(연령 대신), `weight`(kg, decimal), `bcs`(신체조건점수 1~5)를 요구하는데, 현재 IA 화면 입력 항목은 "나이", "크기(소형/중형/대형)"뿐입니다. 화면 입력 항목 자체를 바꿔야 하는 문제라 PD와 별도 협의가 필요합니다(4장 참고).

### 2.3 product-service

| 기능 | API(안) | 권한 | 근거/비고 |
| --- | --- | --- | --- |
| 카테고리/탭별 상품 리스트 | `GET /products?category=&petId=` | MEMBER | 정렬/적합도 점수는 AI 추천 API 결과와 병합 |
| 상품 상세 | `GET /products/{id}` | MEMBER | 영양성분·알레르기·소비기한 등 |
| 영양성분 분석 (AI 위임) | `GET /products/{id}/nutrition-analysis` | MEMBER | 내부적으로 AI `POST /v1/feeds/analyze` 호출·캐싱 |
| 상품 비교 | `POST /products/compare` | MEMBER | 상품ID 배열 입력 |
| 검색(키워드) / 자연어검색 위임 | `GET /products/search?q=` | MEMBER | 자연어 검색은 AI 레포 프록시(유즈케이스에 "AI 기능"으로 명시) |
| 타임딜 목록/알림신청 | `GET /timedeals`, `POST /timedeals/{id}/notify-toggle` | MEMBER | 진행중/오픈예정 탭, 알림은 notification-service로 위임 |
| 최근 본 상품 | `GET /products/recent-viewed` | MEMBER | 최대 9개 |
| 재입고 알림 신청 | `POST /products/{id}/restock-alerts` | MEMBER | 재고 이벤트 발생 시 notification-service 트리거 |
| (백오피스) 상품/타임딜 등록·수정 | `POST/PUT/DELETE /products`, `/timedeals` | **ADMIN(미정의)** | IA 문서 최하단 "백오피스" 항목이 공란 — 4장 이슈 |
- 백오피스 로직 결정에 따라 추가 예상됨

### 2.4 order-service (장바구니 포함)

| 기능 | API(안) | 권한 | 근거/비고 |
| --- | --- | --- | --- |
| 장바구니 CRUD | `GET/POST/PUT/DELETE /cart/items` | MEMBER | 타임딜 상품은 장바구니 우회 가능(바로구매) |
| 체크아웃(주문 생성) | `POST /orders` | MEMBER | product-service(재고 확인/차감), payment-service 호출/SAGA 시작 |
| 주문/배송 내역 조회 | `GET /orders`, `GET /orders/{id}` | MEMBER | 상태: 결제완료/상품준비/배송중/배송완료/구매확정 |
| 구매확정 | `POST /orders/{id}/confirm` | MEMBER | 수동 확정 또는 배송완료 후 7일 자동 확정(SYSTEM 배치) |
| 취소/반품/교환 문의 | `POST /orders/{id}/inquiries` | MEMBER | MVP 범위 — CS 처리 주체는 4장 참고 |
| 주문상태 자동 전이 | `(스케줄러)` | SYSTEM | 유즈케이스: "N시간/N일 경과 후 시스템이 전환" — MVP는 배치 방식으로 가정 |
| 배송 상태 반영 | `PUT /orders/{id}/shipping-status` | EXTERNAL | 배송사 연동 방식(실시간 API vs 배치) 미정 — 4장 참고 |
- 배송은 그냥 임의로 처리해야 함

## 3. 서비스 간/외부/타 직군 통신 정리

### 3.1 동기 호출 (Sync, REST/gRPC)

| 호출 주체 | 대상 | 목적 |
| --- | --- | --- |
| order-service | product-service | 체크아웃 시 재고 확인·차감, 상품 스냅샷(가격/용량) 조회 |
| order-service | payment-service | 결제 요청/취소 |
| order-service | member-service | 결제 화면 진입 시 배송지 스냅샷 조회 |
| review-service | member-service | 리뷰 필터링용 반려동물 프로필 조건(종/나이/체급 등) 조회 |
| review-service | order-service | 리뷰 신뢰도 표시용 구매횟수·사용기간 조회 |
| product-service | AI 레포 | 영양성분 분석(`/v1/feeds/analyze`), 자연어 검색, 홈 화면 추천 API |
| gateway | 전 서비스 | 라우팅 |

### 3.2 비동기 이벤트 (Kafka)

| 발행 | 이벤트 | 구독 | 목적 |
| --- | --- | --- | --- |
| auth-service | `UserSignedUp` | member-service, notification-service | 초기 프로필 온보딩 트리거, 웰컴 알림 |
| order-service | `OrderPaid` | product-service, notification-service, AI 레포 | 재고 확정 차감, 결제완료 알림, orders/order_items 반영 |
| order-service | `OrderStatusChanged` | notification-service | 배송중/완료 알림 |
| order-service | `OrderConfirmed`(구매확정) | review-service | "작성 가능한 리뷰" 목록 반영 |
| review-service | `ReviewCreated` | AI 레포 | reviews·review_features·review_embeddings 생성 트리거 |
| product-service | `RestockDetected` | notification-service | 재입고 알림 신청자 발송 |
| product-service/order-service/review-service | `behavior_events`(view/cart/purchase 등) | AI 레포 | 추천 모델 피처 (**적재 주체 미정 — 4장 참고**) |
| member-service | `MemberWithdrawn` | 전 서비스 | 개인정보 cascade 삭제/익명화 |

### 3.3 외부 시스템 통신

| 대상 | 담당 서비스 | 비고 |
| --- | --- | --- |
| 카카오/구글 OAuth | auth-service | - |
| SMS/알림톡 벤더 | auth-service | 전화번호 인증 |
| PG사(카드/토스/카카오페이/네이버페이) | payment-service | 승인·웹훅·환불 |
| 배송사 API | order-service | 실시간 연동 여부 미정 |
| 주소 검색 API | member-service | 배송지 추가 화면 |
| S3/CDN | member-service, review-service, product-service | 이미지 저장 |
| 노션 페이지 | (프론트 직접 이동) | 신고/1:1문의/입점문의 — MVP는 백엔드 미개입 |

### 3.4 타 직군 통신

- **AI 레포**: 카탈로그·리뷰·주문·행동로그를 이벤트/시드SQL로 제공, 추천·영양분석·재구매예측 API를 소비. `recommendation_id` 트래킹 계약이 프론트까지 걸쳐 있어 3자(백엔드-AI-프론트) 협의가 필요합니다.
- **프론트엔드**: 화면별 API 계약(OpenAPI) 확정 필요. 특히 `behavior_events` 적재를 위한 클라이언트 이벤트 전송 규격.
- **인프라팀**: Kafka/Redis/Elasticsearch 프로비저닝, AI 레포와의 네트워크 정책(동일 클러스터 여부), pgvector 확장 설치 위치.
- **PM/PD**: 백오피스(운영자) 화면 자체가 정의되어 있지 않음 — 가장 시급한 협의 대상입니다.

## 4. AI 팀 요청사항 정리

| 요청 테이블/API | 요청 파트 | 관련 백엔드 기능·화면 | 데이터 적재 주체 | 확인·협의 필요 사항 |
| --- | --- | --- | --- | --- |
| `users.user_id` | 전 파트 | 로그인/회원가입 | 백엔드(auth/member) | 이메일·인증 등 나머지 필드는 백엔드 자율 — 확정 진행 가능 |
| `pet_profile`, `pet_profile_history` | 재구매·추천·영양 | 반려동물 프로필 등록/수정 | 백엔드(member-service) | `birth_date`/`weight`/`bcs` 필드가 현재 IA 입력항목과 불일치 |
| `product_groups`, `product_master` | 재구매·추천·영양 | 상품 등록(백오피스) | 백엔드(product-service) | 백오피스 미정의 상태라 등록 주체·플로우 자체가 없음 |
| `orders`, `order_items` | 재구매·추천 | 결제/주문내역 | 백엔드(order-service) | 프로모션ID·용량 스냅샷 등 필드가 많아 order-service 스키마에 처음부터 반영 필요(직전 논의의 "주문 시점 스냅샷" 원칙과 부합) |
| `behavior_events` | 추천 | 상품조회/찜/장바구니/구매 전반 | **미정** | 여러 서비스에 걸친 이벤트를 어디서 최종 적재할지 소유 서비스 결정 필요 |
| `reviews`(AI 학습용) | 추천·리뷰분석 | 리뷰 작성 | 백엔드(review-service) | review-service 운영 스키마와 AI 학습용 스키마(`usage_scope`, `data_origin` 등)가 달라 별도 동기화 파이프라인 필요 |
| `allergen_ingredient_map` 등 안전·영양 기준 4종 | 추천·영양 | 상품상세 영양분석 | AI가 시드 SQL 제공 → 백엔드가 DB에 실행 | 시드 반영 시점·버전 관리 방식(마이그레이션 도구) 합의 필요 |
| `recommendation_runs`/`recommendation_items` | 추천 | 메인 AI추천, 상품추천 화면 | AI 생성, 백엔드는 API 소비 | 영구 저장 여부 미확정(AI측 요청사항 12번) |
| `POST /v1/feeds/analyze` | 영양 | 상품상세 영양성분 섹션 | AI API, 백엔드는 호출+캐싱만 | 캐싱 테이블 설계는 백엔드 소관으로 별도 필요 |
| `repurchase_predictions` | 재구매 | **현재 IA에 대응 화면 없음** | AI 생성 | 어느 화면/알림에 노출할지 PM 협의 선행 필요 |
| `product_embeddings`/`review_embeddings`(pgvector) | 추천 | 검색/추천 내부 로직 | AI 생성 | pgvector가 백엔드 DB 확장인지 AI 자체 DB인지 미정 — 인프라 협의 대상 |

## 5. 미흡한 부분 · 추가 합의 필요 사항

1. **백오피스(운영자) 기능이 통째로 미정의** — 상품/타임딜/쿠폰 등록, 리뷰 신고 처리, 문의 응대를 누가·어떤 화면으로 할지 IA 문서에 공란으로 남아 있습니다. product-service 등록 API, ADMIN 권한 체계 설계가 이것 없이는 진행되기 어렵습니다.
2. **반려동물 프로필 필드 불일치** — AI가 요구하는 `birth_date`/`weight`(kg)/`bcs`(1~5)가 현재 화면 입력 항목("나이", "크기: 소형/중형/대형")과 다릅니다. 급여량 계산(RER/MER)의 정확도에 직접 영향을 주는 값이라 PD와 화면 수정을 협의해야 합니다.
3. **`behavior_events` 적재 파이프라인 소유 서비스 미정** — product/order/review 세 서비스에서 발생하는 이벤트를 한 곳에 모아야 하는데, 지금 구조상 자연스러운 소유자가 없습니다. 경량 이벤트 수집기를 별도로 둘지, 특정 서비스에 귀속시킬지 결정이 필요합니다.
4. **리뷰 스키마 이원화** — review-service의 운영 리뷰 데이터와 AI 학습용 `reviews` 스키마(출처·합성여부 등)가 다릅니다. 변환·동기화 배치 또는 이벤트 파이프라인 설계가 필요합니다.
5. **pgvector 위치 미정** — 백엔드 DB(product/review)의 확장으로 둘지, AI 레포가 별도 벡터DB를 운영할지에 따라 인프라 구성이 달라집니다.
6. **신고/1:1문의/입점문의가 전부 노션 외부 링크** — MVP에서는 의도된 설계로 보이나, 신고 데이터가 백엔드에 전혀 쌓이지 않는다는 뜻이라 향후 정식 CS 처리가 필요한 시점(리뷰 신고 급증 등)에 대한 대비책을 미리 논의해두는 편이 좋습니다.
7. 쿠폰/프로모션 도메인 공백 — IA에는 "내 쿠폰" 화면이 있지만 지금까지의 서비스 설계에는 쿠폰 도메인이 없습니다. product-service의 서브 도메인으로 추가하거나 별도 검토가 필요합니다.
8. **회원탈퇴 cascade 정책** — "우리 아이의 모든 정보가 날아갈 수 있어요"라는 안내 문구와 달리, 세법상 주문 이력은 일정 기간 보존해야 할 수 있습니다. 무엇을 삭제하고 무엇을 익명화 보존할지 법무 검토가 필요하며, 이전에 논의한 진료내역 보안 이슈와 함께 다뤄야 합니다.
9. **타임딜 동시성·1인1구매 제한** — 유즈케이스상 타임딜은 장바구니를 우회해 바로 결제로 진입합니다. order-service에 타임딜 전용 체크아웃 플로우와, 1인1구매 제한을 검증하는 별도 로직(Redis 기반 락/카운터)이 필요합니다. 인프라 아키텍처 논의 때 다룬 재고 동시성 이슈와 직결됩니다.
10. **`recommendation_id` 트래킹 계약** — `behavior_events.recommendation_id`를 채우려면 AI 추천 API 응답에 포함된 ID를 프론트가 각 클릭/장바구니/구매 이벤트에 실어 백엔드로 보내야 합니다. 프론트·AI·백엔드 3자 협의가 필요한 항목입니다.
11. **배송사 연동 방식 미정** — 유즈케이스는 "N시간 경과 후 시스템이 상태를 전환한다"고만 되어 있어, MVP는 실제 배송사 API 연동 없이 배치 스케줄러로 상태를 흉내 내는 것으로 가정했습니다. 실연동 여부와 시점을 PM과 확인해야 합니다.
12. **랜덤 닉네임 자동생성 로직의 소유 서비스** — 회원가입 시점(auth) 이벤트인지, 프로필 조회 시 필요한 값(member)인지에 따라 구현 위치가 달라집니다. 사소해 보이지만 회원가입 트랜잭션 경계에 영향을 줍니다.
