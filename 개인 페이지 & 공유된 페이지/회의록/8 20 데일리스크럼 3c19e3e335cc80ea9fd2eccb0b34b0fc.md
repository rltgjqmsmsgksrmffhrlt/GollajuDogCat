    - 타임딜 오픈 관련 알림을 보낸다면 해당 배치 처리는 알림에서 하는지

        - AI도 관련 도메인이 있다면(유저 데이터 기반, 상품 데이터 기반)상세하게 나누어야 할지

        - 추천 결과 API를 따로 만들어서 프론트에서 호출 or 주문 API와 연계해서 응답

### 피드백 정리

- 강사님 피드백 정리
    
    ### 1. 타임딜을 별도 마이크로서비스로 분리할지
    
    - **결론: 분리하지 말고 상품 서비스에 포함하는 게 낫다**는 멘토 의견
    - 이유: 타임딜은 결국 "상품에서 옵션(만료기한, 할인) 몇 개가 달라지는 것"뿐이라, 굳이 서비스를 통째로 나눌 정도는 아님
    - **스케일아웃도 "타임딜이라서"가 아니라 "병목 지점이 어디인지"를 먼저 파악하고 결정해야 함** — 검색이 몰리는지, 주문이 몰리는지 구체화 안 하면 "그냥 나누자"는 근거가 약함
    - 부하 테스트 결과 병목이 DB/검색엔진이면 그쪽을, 주문/결제가 병목이면 그쪽을 스케일아웃하는 식으로 접근
    
    ### 2. 미리 병목 지점을 예상해서 나눠야 하는지
    
    - 미리 나눌 수는 있지만, **"이럴 것 같아서 나눴어요"라고만 답하면 면접에서 반드시 추가 질문을 받는다**는 현실적 조언
    - 실제로 부하테스트를 안 해봤다면 근거가 약해지니, "예상은 해보되 실제 방향은 달라질 수 있다"고 솔직히 말하는 게 낫다는 것
    
    ### 3. 타임딜 오픈 알림 — 누가 담당해야 하나
    
    - **알림 서비스가 담당하는 게 맞음** — 타임딜 서비스가 아니라, 알림 조건(1일 전, 몇 시간 전 등)에 맞춰 알림 서비스가 배치로 처리
    - 정책이 구체화돼야 세부 구현이 달라짐 (참고만 하라는 조언)
    
    ### 4. 타임딜 시작 시간에 맞춰 "구매 가능" 상태로 자동 전환하는 방법
    
    - 스케줄링으로는 초 단위 정확도가 떨어질 수 있음
    - **Redis TTL을 검색해보라는 조언** — 상품에 TTL(예: 1시간)을 걸어두면, 시간이 되는 순간 백엔드가 신호를 받아 상태를 변경하는 방식 제안
    
    ### 5. 타임딜 재고가 남으면 원래 상품 재고로 되돌려야 하는지
    
    - **기획에 따라 다름** — 재고가 남으면 다음 시즌 상품으로 이월하거나 할인 판매하는 등, 정책 나름이라 정답은 없음
    
    ### 6. AI 데이터 저장 (RDB vs NoSQL)
    
    - AI 응답이 정형 데이터가 아니라 긴 텍스트일 가능성이 높음 → RDB보다 **검색엔진(ES)이나 MongoDB**가 적합할 수 있음
    - 다만 **"AI 데이터가 정확히 어떤 형태로 오는지" 먼저 파악하고, AI팀과 직접 협의해서 결정**해야 함(선행 조건)
    
    ### 7. AI 관련 데이터를 별도 마이크로서비스로 관리해야 하는지
    
    - **불필요** — AI팀 규모(3명)와 통신 빈도를 고려하면, 단순 REST(HTTP)나 gRPC 통신으로 충분
    - 하나의 마이크로서비스(예: 주문) 안에서 RDB와 다른 DB(NoSQL)를 같이 쓰는 것도 무방 — **마이크로서비스는 도메인 단위로 나누는 것이지, DB 개수를 제한하는 게 아님**
    
    ### 8. AI 서버로 데이터 보낼 때 Kafka vs 동기 호출
    
    - **유실 방지가 중요하거나 실시간 파이프라인이 필요하면 Kafka**, 아니면 단순 비동기 HTTP(WebClient)로도 충분
    - 무조건 이벤트 기반(Kafka)으로 가는 게 트렌드라서가 아니라, **실제 요구사항(유실 허용 여부)에 따라 판단**해야 함
    
    ### 9. 추천 결과를 프론트에 어떻게 보여줄지
    
    - **AI 서버를 프론트가 직접 호출하는 방식보다, 일반 API 서버가 AI가 저장해둔 DB를 조회해서 응답하는 방식이 보안상 더 낫다**는 조언
    
    ### 10. 공통 응답 포맷 — ProblemDetail vs 커스텀 DTO vs ResponseEntity
    
    - ProblemDetail(Spring 6+ 표준)은 최신 트렌드에서 많이 쓰이는 편, 안 써봤으면 써보는 것도 좋음
    - 실무에선 보통 **ResponseEntity로 감싸서 반환**하는 방식이 일반적
    - 결국 **"내부적으로 어떻게 설계하느냐"에 달린 문제**라 정답은 없고, 표준화만 잘 해두면 됨
    
    ### 11. TraceID — 클라이언트에 노출할지, 게이트웨이에서 생성할지
    
    - **클라이언트에는 노출하지 말고 내부 로깅용으로만 사용**하는 게 맞음
    - 특히 비동기 통신에서 다른 서버 응답이 안 왔을 때 페이로드 추적용으로 씀
    
    ### 12. 서버 간 인증 — mTLS vs SG+시크릿헤더
    
    - **결론**: mTLS는 "제로 트러스트"를 하려는 것이고, 도입하면 **지금 짜는 코드(CC/시크릿헤더)가 전부 필요 없어짐**
    - **mTLS는 인프라(쿠버네티스 담당자)가 관리할 영역**이라 코드보다 인프라적으로 접근하는 게 맞음
    - **2번(Gateway로 모든 요청 강제)은 네트워크 트래픽이 느려지는 단점**이 있어 장단점을 고려해 결정
    - **mTLS는 "나중에 여유되면"으로 미뤄진 상태** — 지금은 코드 단(시크릿값)으로 진행하는 게 현실적이라는 결론
    
    ### 13. 검색 도메인 분리 여부
    
    - 통합 검색으로 갈 거면 별도 마이크로서비스로 분리하는 게 좋다는 의견 — 다만 이러면 작업량이 커짐
    
    ### 14. AI 필요 데이터에 따라 기능이 많아진다면 어떻게 조율해야 할지
    
    - **판단 순서**: ① 그 기능에 필요한 데이터가 실제로 나올 수 있는지 먼저 확인 → ② 데이터가 충분한지 확인 → ③ 그래도 필요하면 우선순위를 정해서 "높은 것부터 하나씩 해드리겠다"고 조율
