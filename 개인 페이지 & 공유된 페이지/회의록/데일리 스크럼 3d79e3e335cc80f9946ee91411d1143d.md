### 2. 이번 프로젝트의 점검 방식

현재 체크리스트 기준으로는 **Ansible 중심으로 갈 필요가 없음**.

점검 방식은 크게 3가지로 분류하면 됩니다.

| 분류 | 주요 대상 | 방법 |
| --- | --- | --- |
| 웹 애플리케이션 수동 점검 | 인증·인가, 결제, 비즈니스 로직, API 등 | Burp Suite 등으로 실제 기능·HTTP 요청 확인 |
| AWS 설정 점검 | IAM, VPC, Security Group, S3, RDS 등 | AWS CLI + 전체 리소스 Read 권한 |
| 인터뷰·증적 확인 | 개발 공급망, 계정 관리, 백업·복구 정책 등 | 담당자 인터뷰 + 설정 화면·문서 증적 |

즉, 지금 해야 할 중요한 작업은 **60개 항목 각각을 위 점검 방식 중 하나로 분류하는 것**입니다.

### 3. Ansible에 대한 결론

이번 프로젝트에서는 **Ansible이 필수적이지 않음**.

Ansible은 주로 실제 서버 OS에 접속해서 다음과 같은 설정을 여러 서버에서 일괄 확인할 때 효과적입니다.

예:

- `/etc/ssh/sshd_config`
- `PermitRootLogin no`
- 계정/패스워드 정책
- 파일 권한
- 설치 패키지 버전
- 서비스 실행 상태

서버가 수십~수천 대라면 Ansible로 스크립트를 일괄 실행하는 의미가 있습니다.

하지만 현재 체크리스트의 인프라 영역은 대부분 **AWS 리소스 설정 점검**이므로 AWS CLI로 충분합니다.

따라서:

> 프로젝트 점검용 Ansible 환경 구축은 우선순위에서 제외해도 됨.
> 
> 
> 다만 개인 실습·포트폴리오 목적으로 Ansible을 별도로 사용해 보는 것은 가치가 있음.
> 

### 4. 가장 먼저 요청해야 할 사항

인프라 팀에 가장 먼저 요청할 것은 **AWS 전체 리소스 조회용 Read 권한 계정 또는 Role**입니다.

목적은 AWS CLI를 통해 다음과 같은 설정을 직접 확인하기 위한 것입니다.

- IAM
- VPC
- Security Group
- EC2
- ECS/EKS
- S3
- RDS
- CloudTrail
- CloudWatch
- 기타 사용 중인 AWS 리소스

요청 취지는 다음 정도면 됩니다.

> 보안 점검을 위해 AWS CLI에서 사용 중인 리소스의 설정 상태를 조회할 수 있도록 전체 리소스에 대한 ReadOnly 수준의 권한이 필요합니다. 변경 권한은 필요하지 않습니다.
> 

### 5. 점검 전 사전 준비

9월 18일 전까지 해야 할 핵심 작업입니다.

**보안팀 내부 준비**

- 60개 점검 항목을 점검 방식별로 분류
- 각 항목의 실제 점검 절차 정의
- Burp Suite 점검 환경 준비
- AWS CLI 점검 명령 정리
- 인터뷰 질문 목록 작성
- 필요한 증적 목록 작성
- 판정 기준 정리
- 결과 기록 형식 정리

**다른 팀에 미리 요청할 것**

- AWS Read 권한
- 필요한 계정
- 테스트 가능한 서비스 URL
- 테스트 계정
- 역할별 계정이 필요하다면 일반 사용자/관리자 등의 테스트 계정
- 인터뷰가 필요한 담당자
- 점검에 필요한 문서 및 증적

증적을 요청할 때 단순히 `"IAM 설정 캡처 주세요"`라고 하지 말고 **어느 화면에서 무엇이 보이도록 캡처해야 하는지 예시까지 제공하는 것이 좋다**는 의견도 나왔습니다.

### 6. Burp Suite + MCP + AI 활용

웹 애플리케이션 점검은 다음 구조로 진행할 수 있습니다.

**웹 서비스 → Burp Suite → HTTP History → Burp MCP → AI**

웹서비스의 기능을 직접 사용하면서 Burp에 HTTP 요청·응답을 충분히 쌓고, AI가 MCP를 통해 해당 데이터를 분석하도록 하는 방식입니다.

여기서 중요한 것이 멘토가 말한 **Harness**입니다.

Harness는 별도 특별한 프로그램이라기보다:

> AI에게 **무엇을, 어떤 기준으로, 어떤 절차로 점검하고, 결과를 어떻게 출력할지 정의한 작업 규칙**
> 

이라고 보면 됩니다.

현재 여러분이 만든 **60개 체크리스트가 Harness의 기반**이 됩니다.

### 7. Harness 구성 방법

하나의 거대한 MD 파일로 만들 필요는 없습니다.

현재 체크리스트의 영역 단위로 분리하는 것이 적절합니다.

예:

```
security-assessment/
 ├─ README.md
 ├─ A_authentication.md
 ├─ B_authorization.md
 ├─ C_business_logic.md
 ├─ D_api_security.md
 ├─ F_cloud_infrastructure.md
 └─ H_supply_chain.md
```

각 MD 내부는 대략 다음 구조면 충분합니다.

```
# C. Business Logic

## C-01 결제 금액 검증

### 점검 목적

### 점검 절차

### 확인할 HTTP 요청

### 판정 기준

### 증적

### 결과 작성 형식
```

너무 세세한 프롬프트를 작성하기보다 **점검 목적·절차·판정 기준을 명확히 정의하는 것이 중요**하다는 의견입니다.

### 9. 보고서 구조

보고서는 최소 3단계로 생각하면 됩니다.

**① 최초/1차 점검 보고서**

60개 체크리스트를 실제 점검한 결과입니다.

예:

| 항목 | 결과 | 발견사항 | 개선 방향 |
| --- | --- | --- | --- |
| C-01 | 미흡 | 결제수량 서버 검증 없음 | 서버에서 최소·최대 수량 검증 |
| F-01 | 양호 | IAM 최소권한 적용 | - |

코드까지 직접 작성해줄 필요는 없고 **수정 방향을 구체적으로 설명하는 수준이면 충분**합니다.

**② 이행 점검 보고서**

1차 결과에서 미흡했던 항목만 다시 확인합니다.

예:

| 항목 | 1차 | 조치내용 | 이행점검 |
| --- | --- | --- | --- |
| C-01 | 미흡 | 서버 수량 검증 추가 | 양호 |
| F-01 | 양호 | - | 양호 |

기본적으로 **1차 점검 시트를 복사해 변경사항과 새로운 판정만 기록**해도 됩니다.

**③ 최종 결과 보고서**

프로젝트 종료 시점의 최종 상태를 정리합니다.
