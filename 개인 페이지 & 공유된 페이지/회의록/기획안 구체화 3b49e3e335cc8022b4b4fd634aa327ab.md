# 기획안 구체화

해당 스프린트: Sprint 1
유형: 데일리 스크럼
참석자: ALL
과정: 팀장 데일리 스크럼
날짜: 2026년 8월 6일

### 서비스 방식

**모듈 방식보다는 자체 통합 서비스로 구축**

모듈 형태로 제공할 경우 배달 플랫폼마다 사용하는 프로그래밍 언어, 시스템 구조, 주문·결제 API, 보안 및 개인정보 처리 정책이 달라 플랫폼별 연동 개발이 필요하다. 이로 인해 초기 개발 범위와 유지보수 비용이 커지고, 플랫폼에 따라 제공할 수 있는 기능과 사용자 경험이 달라질 수 있다.

따라서 초기에는 **AI 음성 대화, 메뉴 검색 및 추천, 반복 주문, 주문 내용 확인, 보호자 승인 기능을 하나의 서비스 안에서 제공하는 자체 통합형 서비스**로 구축한다. 사용자는 전화형 앱 또는 대표 전화번호를 통해 서비스를 이용하고, 보호자는 별도의 보호자 화면에서 주문 내역을 확인하고 승인할 수 있다.

초기 MVP에서는 제한된 지역과 음식점 메뉴 데이터를 활용해 주문서를 생성하고 보호자에게 전달하는 방식으로 구현한다. 이후 서비스 안정성과 사용성을 검증한 뒤 배달 플랫폼, 지역 음식점, 복지기관 등과 연계할 수 있도록 **공통 API 또는 SDK 형태의 모듈로 확장**한다.

> **초기에는 독립적인 통합 서비스로 핵심 사용자 경험을 검증하고, 이후 표준화된 API를 통해 외부 플랫폼으로 확장한다.**
>

### 보안

개인정보 제 3자 제공 여부

#### 1. 개인정보 및 보안 문제

> 음성 주문 과정에서 다음 정보가 처리될 수 있어 개인정보 보호 문제가 발생할 수 있다는 피드백입니다.
> 
- 사용자 이름과 연락처
- 배달 주소
- 주문 이력과 선호 메뉴
- 결제 관련 정보
- 보호자 정보
- 알레르기 등 개인 특성
- 사용자의 음성 데이터

특히 기존 배달 플랫폼의 데이터를 외부 서비스가 처리하면 개인정보 제3자 제공 또는 처리위탁 문제가 발생할 수 있습니다.

#### 2. 기존 플랫폼 의존성

- 배민·요기요 등이 공식 API를 제공하지 않으면 안정적인 주문 연동이 어려움
- 화면 크롤링이나 자동 클릭은 UI가 변경되면 작동하지 않을 수 있음
- 플랫폼마다 기술 스택과 데이터 형식이 달라 호환이 어려움
- 기존 플랫폼의 정책과 이용약관에 영향을 받음
- 플랫폼 협력이 없으면 실제 주문과 결제 단계 구현이 제한될 수 있음

#### 3. 기존 플랫폼의 도입 가능성

- 배민·요기요가 외부 스타트업 기술을 채택할 이유가 충분한가?
- 플랫폼 내부 개발 인력으로 유사 기능을 직접 만들 수 있지 않은가?
- 외부 서비스를 도입하면 개인정보와 보안 관리 부담이 증가하지 않는가?
- 스타트업의 기술과 인프라를 플랫폼에 맞추는 데 비용이 많이 들 수 있음
- 아이디어가 검증되면 기존 플랫폼이 유사 기능을 자체 개발할 가능성이 있음

#### 4. 별도 서비스 운영 문제

> 고령층 전용 배달앱을 별도로 만들 경우 다음 문제가 있다는 피드백입니다.
> 
- 음식점과 메뉴 데이터 확보 필요
- 결제와 주문 시스템 구축 필요
- 배달 플랫폼 운영비용 발생
- 사용자를 새 앱으로 유입해야 함
- 기존 배달 플랫폼과 기능이 중복될 수 있음

따라서 완전한 신규 배달 플랫폼보다는 기존 주문 인프라를 활용하는 방안이 효율적이라는 의견입니다.

#### 5. 시장성과 수익성 문제

- 고령층의 실제 배달 주문 수요가 충분한가?
- 주 이용층인 20~40대보다 주문 빈도와 결제 금액이 낮지 않은가?
- 고령층만을 대상으로 지속적인 수익을 만들 수 있는가?
- 플랫폼이 비용을 지불할 만큼 새로운 주문을 발생시킬 수 있는가?
- 수익모델과 비용 지불 주체가 불명확함

사용자는 고령층이지만 비용을 지불하는 고객은 플랫폼, 프랜차이즈, 보호자, 지자체 또는 돌봄기관이 될 수 있다는 구조를 추가로 검토할 필요가 있습니다.
