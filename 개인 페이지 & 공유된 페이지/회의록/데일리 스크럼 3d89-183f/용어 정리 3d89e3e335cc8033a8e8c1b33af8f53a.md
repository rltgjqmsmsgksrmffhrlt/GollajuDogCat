# 용어 정리

1. 하이브리드 코드 / 하이브리드 앱

**네이티브 앱과 웹 기술이 섞인 앱**입니다. Android 앱 전체를 Kotlin/Java로 만들거나 iOS 앱 전체를 Swift로 만드는 대신, HTML·CSS·JavaScript 같은 웹 기술로 화면이나 로직을 만들고 이를 모바일 앱 내부에서 실행합니다.

Android에서는 대표적으로 `WebView`라는 구성요소를 이용해 앱 안에서 웹 콘텐츠를 표시할 수 있습니다. Android 공식 문서에서도 WebView를 웹 콘텐츠와 네이티브 컴포넌트를 함께 사용하는 **하이브리드 앱의 용도**로 설명합니다.

예를 들면:

```
Android / iOS 앱
       │
       ├─ 네이티브 영역
       │   ├─ 카메라
       │   ├─ GPS
       │   └─ 알림
       │
       └─ WebView 영역
           ├─ HTML
           ├─ CSS
           └─ JavaScript
```

그래서 보안 점검 관점에서는 일반 웹 점검과 달리 **앱 자체 + WebView + 네이티브-웹 연결부(JavaScript Bridge) + API 통신**까지 볼 수 있습니다.

다만 **“하이브리드 코드”라는 표현 자체가 엄밀한 기술명은 아닙니다.** 보통은 “하이브리드 앱” 또는 “하이브리드 앱 코드”라고 표현합니다.

1. **크로스 컴파일(Cross Compilation)**

크로스 컴파일은 **코드를 컴파일하는 환경과 실제 실행될 환경이 다른 것**을 의미합니다.

예를 들어 Windows나 macOS 개발 PC에서 코드를 빌드하지만 결과물은:

```
개발 PC
   │
   │ 컴파일
   ▼
Android APK
   │
   ▼
Android 기기에서 실행
```

처럼 다른 플랫폼을 대상으로 만들 수 있습니다.

GCC에서도 `build`, `host`, `target`이라는 개념으로 이를 구분하며, **컴파일을 수행하는 시스템과 생성되는 코드의 대상 시스템이 다른 경우 cross compiler를 사용한다**고 설명합니다.

다만 여기서 하나 주의해야 합니다.

**“Android와 iOS 둘 다 만들 수 있다 = 무조건 크로스 컴파일”은 아닙니다.**

예를 들어 Flutter, React Native, Kotlin Multiplatform 같은 **크로스 플랫폼 개발**과 크로스 컴파일은 서로 관련은 있지만 정확히 같은 개념은 아닙니다.

멘토님이 말한 맥락에서는 아마:

```
하나의 코드베이스
        ↓
 Android용 앱
        +
   iOS용 앱
```

형태의 **크로스 플랫폼 개발**을 의미했을 가능성이 큽니다.

그러므로 프로젝트 문서에는 현재 단계에서

**“Android/iOS 크로스 플랫폼 또는 하이브리드 방식으로 개발되는 것으로 가정”** 정도로 적는 게 기술적으로 더 안전합니다.

1. **rever-browser**

이건 실제로 존재하는 도구입니다. `rever-browser`는 **웹 애플리케이션/API 리버스 엔지니어링을 지원하는 AI 기반 브라우저 도구**입니다.

프로젝트 설명에 따르면 Chromium 기반 브라우저를 띄우고 Chrome DevTools Protocol(CDP)을 이용해 브라우저에서 발생하는 네트워크 요청을 수집합니다. 그리고 AI 에이전트가 해당 요청이나 JavaScript 코드를 분석할 수 있습니다.

구조를 단순화하면:

```
웹사이트 접속
    ↓
rever-browser
    ↓
브라우저에서 발생한
HTTP/API 요청 수집
    ↓
AI 분석
    ↓
API 구조 / 요청 / JS 분석
```

기능에는 네트워크 트래픽 캡처뿐 아니라 페이지 클릭·입력·스크롤 같은 브라우저 자동화와 JavaScript bundle 분석, request repeater 등의 기능도 포함되어 있습니다.

그래서 멘토님이 말한

> “rever-browser는 웹 패킷 잡는 거였다”
> 

는 표현은 대략적인 설명으로는 맞지만 정확히는 **단순 패킷 캡처 툴이라기보다 웹 브라우저의 HTTP/API 트래픽을 수집하고 분석·자동화하는 도구**입니다.

Wireshark처럼 TCP/IP 수준의 패킷을 캡처하는 도구라고 생각하면 안 됩니다.

1. **appium → 정확한 이름은 `Appium`**

멘토님이 말씀한 `applium`은 거의 확실하게 **Appium(앱피움)**을 말한 것으로 보입니다.

Appium은 **모바일 앱 등의 UI 조작을 자동화하는 오픈소스 도구**입니다. Android, iOS뿐 아니라 웹, 데스크톱 등 여러 플랫폼의 UI 자동화를 지원합니다.

예를 들어 사람이 직접:

```
앱 실행
→ 로그인 버튼 클릭
→ ID 입력
→ PW 입력
→ 로그인
→ 상품 클릭
→ 결제 화면 이동
```

하는 것을 Appium 코드로:

```
앱 실행
→ 자동 클릭
→ 자동 입력
→ 자동 화면 이동
```

시킬 수 있습니다.

Android에서는 보통 Appium에 **UiAutomator2 Driver**를 연결해서 사용합니다. Appium 공식 Quickstart에서도 Android 자동화를 위해 UiAutomator2 Driver를 설치하는 구조를 안내합니다.

대략적인 구조는 다음과 같습니다.

```
보안 점검 스크립트
       │
       ▼
     Appium
       │
       ▼
UiAutomator2 Driver
       │
       ▼
Android Emulator
       │
       ▼
    점검 대상 앱
```

여기에 Burp를 붙이면:

```
                    ┌─ Appium
                    │   ↓
점검 스크립트 → Android Emulator
                    │
                    │ 앱 통신
                    ↓
                   Burp
                    ↓
                  서버
```

가 됩니다.

즉 **Appium이 패킷을 잡는 것이 아닙니다.**

역할을 정확히 나누면:

**Appium = 앱 조작 자동화**

**Burp Suite = HTTP/HTTPS 통신 가로채기·분석**

**Android Emulator = 앱 실행 환경**

입니다.

Appium 공식 문서 역시 주 목적을 실제 앱 UI에서 사용자 시나리오를 자동 수행하는 **UI automation**이라고 설명합니다.

현재 프로젝트 관점에서 네 용어의 관계를 한 번에 보면 다음처럼 이해하는 게 가장 정확합니다.

```
[개발 방식]

하이브리드 / 크로스 플랫폼 앱
           │
           ▼
     Android APK
           │
           ▼
   Android Emulator
           │
     ┌─────┴─────┐
     ▼           ▼
   Appium       Burp
     │           │
 UI 자동조작   HTTP/HTTPS 분석
     │           │
     └─────┬─────┘
           ▼
       보안 점검
```

그리고 **rever-browser는 이 구조에 직접 들어가는 도구라기보다는 기존 웹 애플리케이션 점검에서 브라우저 트래픽/API 분석과 브라우저 자동화를 담당하던 도구**에 더 가깝습니다. 모바일 앱으로 점검 범위가 바뀌면서 그중 **UI 자동화 역할을 Appium이 가져오는 것**으로 이해하면 현재 멘토링 내용과 잘 맞습니다.

1. **안드로이드 에뮬레이터(Android Emulator)**

안드로이드 에뮬레이터는 **PC 안에서 가상의 Android 기기를 실행하는 프로그램**입니다. 실제 스마트폰 없이도 Android OS와 앱을 실행하고 테스트할 수 있습니다.

구조는 대략 이렇게 보면 됩니다.

```
PC
└─ Android Emulator
   └─ Android OS
      └─ 점검 대상 앱
```

보안 점검에서는 이 에뮬레이터에 앱을 설치한 뒤, 프록시를 Burp로 지정하거나 루팅 가능한 이미지를 사용해서 인증서 설치, 트래픽 분석, 파일 확인 등을 수행할 수 있습니다.

즉, 지금 프로젝트에서는 **실제 테스트용 스마트폰 대신 사용하는 점검 환경**이라고 이해하면 됩니다.

1. **네이티브 앱(Native App)**

네이티브 앱은 **특정 운영체제를 대상으로 직접 개발한 앱**입니다.

대표적으로:

```
Android
→ Kotlin / Java

iOS
→ Swift / Objective-C
```

처럼 운영체제별 기술을 사용합니다.

예를 들어 Android에서 버튼 하나를 만든다면 Android의 UI 컴포넌트를 직접 사용하고, 카메라·GPS·블루투스·파일 시스템 같은 기기 기능도 Android API를 통해 직접 접근합니다.

```
네이티브 앱

Android App
   │
   ├─ Android UI
   ├─ Android API
   ├─ Camera
   ├─ GPS
   └─ Storage
```

장점은 성능과 OS 기능 연동이 좋다는 것입니다.

반대로 Android와 iOS를 모두 지원하려면 보통 플랫폼별 개발이 필요합니다.

```
Android용 코드
+
iOS용 코드
```

그래서 하나의 코드베이스를 여러 플랫폼에서 사용하려는 목적으로 하이브리드 앱이나 크로스 플랫폼 프레임워크를 사용하기도 합니다.

1. **WebView**

WebView는 **앱 안에 들어가는 작은 웹 브라우저 같은 컴포넌트**입니다.

예를 들어 Android 앱을 실행했는데 화면 일부가 HTML, CSS, JavaScript로 구현되어 있다면 WebView 안에서 해당 웹 콘텐츠를 실행할 수 있습니다.

```
Android App

┌───────────────────────┐
│ Native 영역            │
│                       │
│   ┌─────────────────┐ │
│   │ WebView         │ │
│   │                 │ │
│   │ HTML            │ │
│   │ CSS             │ │
│   │ JavaScript      │ │
│   └─────────────────┘ │
│                       │
└───────────────────────┘
```

일반 Chrome 브라우저와 가장 큰 차이는 **브라우저가 독립적으로 실행되는 것이 아니라 앱 내부에 포함되어 있다는 점**입니다.

예를 들어 쇼핑 앱에서:

```
로그인 화면 → 네이티브
상품 목록 → WebView
카메라 촬영 → 네이티브
결제 화면 → WebView
```

처럼 섞어서 만들 수도 있습니다.

보안 점검에서는 WebView가 꽤 중요합니다. WebView에서 JavaScript 실행이 허용돼 있는지, 외부 URL을 위험하게 로드하는지, 네이티브 코드와 JavaScript를 연결하는 인터페이스가 안전한지 등을 확인할 수 있기 때문입니다.

세 개의 관계를 한 번에 보면 이렇게 이해하면 됩니다.

```
PC
│
└─ Android Emulator
      │
      └─ Android App
            │
            ├─ Native 영역
            │    └─ Kotlin / Java
            │
            └─ WebView 영역
                 └─ HTML / CSS / JavaScript
```

따라서 **에뮬레이터는 앱을 실행하는 환경**, **네이티브는 앱 구현 방식**, **WebView는 앱 내부에서 웹 콘텐츠를 실행하는 구성요소**입니다.
