## 2. 상황 공유

### 오전 팀장 데일리 스크럼 요약

- 전달해야 될 내용
    - `FE` 추가 완료 기능: 소셜 로그인, 상품 검색
    - `PM` `AI` 검색 + 추천순 관련: 검색 결과에서 추천순 정렬이 AI 기능상 가능한건지
        - 현재 추천 API가 `pet_id` 만 받아서 product db에서 알아서 추천순으로 보내는 것 같은데
        그러면 검색 결과 안에서 추천순으로 정렬하는 기능은 구현이 불가능한게 맞는지
        → 이 경우에 추천순 정렬은 기본 목록 조회에서만 사용하고 검색에서는 제외해야 될 것 같다.
        - 추천 API의 items 반환 개수는 어떻게 처리되는지 (백엔드에서 size로 받는거랑 맞춰지는건지)
    - `AI` `인프라` FeignClient 호출로 생각하고 있으면 될지.. AI 서버는 주소가 다른건지 (호출 URL 관련)
    - `인프라` pg_bigm GIN 인덱스 사용 생각중 (확장을 포함한 PostgreSQL 사용 필요)
- AI 관련 내용은 팀원분들과 확인 후 전달 예정

### 피드백 내용

- 요약
    
    **1. 상품/리뷰/QnA 조회 구조**
    
    - 상품, 리뷰, QnA를 하나의 API로 한 번에 가져올지, 여러 API로 나눠서 가져올지 논의
    - 몽고DB(JSON 형태)로 구성하면 한 번의 API 호출로 빠르게 가져올 수 있지만, RDB 조인으로 처리하면 데이터가 많아질수록 조인 비용(지연)이 커짐
    - 멘토 의견: 데이터/트래픽이 커질 걸 대비해 API를 분리해서(2~3번 호출) 프론트에서 조합하는 방식이 성능상 유리. 다만 시간상 몽고DB 도입이 어려워 최종적으로는 RDB + API 분리 방식으로 결정
    - 클릭 시마다 API를 호출할지(실시간성 확보) 전체를 미리 불러올지도 추가 고민 포인트로 남음
    
    **2. AI 개인화 추천 상품 캐싱**
    
    - 추천 상품은 상품ID + 로그인 사용자의 펫ID 조합으로 AI 서버에서 개인화 응답을 받아오는 구조
    - 개인화 데이터라 저장(캐싱) 여부가 애매함 → 상품 들어올 때마다 추천이 계속 달라지는 경우라면, 레디스/몽고DB 같은 곳에 AI 응답 결과를 저장해두는 방식을 고려 (재조회 시 AI 모델을 매번 호출하지 않도록)
    - 확정된 답은 아니고, 세부 스펙(추천이 매번 바뀌는지 여부)에 따라 접근이 달라짐 → 추후 재논의하기로 함
    
    **3. 배송정보/상세정보 조회**
    
    - 같은 테이블에 있고 조인이 없는 경우엔 한 번에 묶어서 반환해도 무방
    - 다만 배송비 등은 실제로는 판매자 관련 데이터와 분리되어 있을 가능성이 높아 확인이 필요한 상태
    
    **4. 장바구니 스냅샷 vs 실시간 조회**
    
    - 장바구니: 실시간으로 프로덕트 서비스를 호출해서 현재 가격/정보를 보여주는 게 맞음 (포링키 참조가 없다면 장바구니 자체에서 가격/수량을 관리)
    - 주문 내역: 주문 시점의 스냅샷 가격을 저장해서 보여줘야 함 (실무에서도 스냅샷 데이터를 별도 관리)
    - 장바구니 데이터와 주문 데이터는 성격이 다름 — 장바구니는 "담았던 이력", 주문은 "실제 구매 확정 이력"이므로 별개로 관리하는 게 맞음
    
    **5. 리뷰-상품 바운디드 컨텍스트** 
    
    - 리뷰 생성 시 카프카 이벤트를 발행 → 상품 도메인이 이를 받아 리뷰 개수/평점을 업데이트
    - 멘토는 두 가지 경우로 구분:
        - **리뷰를 상품의 하위 요소로 볼 경우**: 프론트는 상품 도메인을 거쳐 리뷰 작업을 하고, 상품→리뷰로 이벤트 발송, 다시 리뷰→상품으로 이벤트 발송해서 카운트 갱신
        - **리뷰를 완전히 별개 도메인으로 볼 경우**: 프론트가 리뷰 도메인에 직접 접근, 리뷰→(큐)→상품으로 이벤트 발송해서 업데이트
