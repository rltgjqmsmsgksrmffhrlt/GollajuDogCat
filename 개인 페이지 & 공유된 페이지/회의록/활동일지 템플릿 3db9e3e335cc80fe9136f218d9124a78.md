### 1. 인증 (Authentication)

- **로그인 방식**: OAuth2 소셜 로그인(카카오/구글) → RSA 서명 기반 JWT(access/refresh) 발급
- **게이트웨이 검증**: JWKS 공개키로 JWT 서명 검증 → 검증된 클레임만 내부 서비스로 전달
- **토큰 타입 검증**: refresh 토큰으로 access 토큰 전용 API를 우회 호출하지 못하도록 `tokenType` 구분
- **헤더 스푸핑 방지**: 클라이언트가 직접 보낸 `X-Auth-Id`, `X-Member-Id`는 게이트웨이가 무조건 제거 후 검증된 값으로 재설정
- **기본값 안전 설계**: 공통 모듈을 통해 모든 서비스가 기본적으로 "인증 필요" 상태로 강제 (개별 서비스의 설정 누락 방지)
- **회원가입 완료 판단 기준 정교화**: "최초 로그인 여부" → "실제 memberId 존재 여부"로 변경 — 로그인은 했지만 가입을 안 끝낸 사용자를 놓치지 않도록 개선
- **토큰 재발급**: 회원가입 완료 시점에 갱신된 인증 정보를 반영해 토큰을 재발급하는 절차 추가

### 2. 암호화 (Encryption)

- **JWT 서명**: 대칭키가 아닌 RSA 비대칭키 사용 — 개인키는 발급 서버만 보유, 검증은 공개키로만 가능
- **타이밍 공격 방지**: 서비스 간 내부 통신 검증용 시크릿 비교 시 문자열 단순 비교 대신 `MessageDigest.isEqual`(상수 시간 비교) 적용

### 3. 보안 통제 (Security Controls)

- **내부 API 보호**: 게이트웨이 우회 접근 차단을 위해 별도 내부 시크릿으로 검증, 신규 내부 API에도 동일 체계 일관 적용
- **인증/인가 실패 응답**: 구체적 실패 사유 노출 금지(오라클 공격 방지) — 일반화된 메시지로만 응답, 상세 사유는 서버 로그에만 기록
- **IDOR 방지**: 리소스 소유권 검증 시 "존재하지 않음"과 "타인 소유"를 구분 못 하게 동일 응답으로 통일 — 회원 프로필, 반려동물 정보, 리뷰 작성 소유권 확인 등에 동일 패턴 적용
- **동시성 방어**: DB 유니크 제약 + 애플리케이션 사전 검증의 이중 방어로 동시 요청 경합 대응
- **장애 vs 정상 상태 구분**: 외부 서비스 호출 실패 시 "정상적으로 존재하지 않음"과 "통신/시스템 장애"를 구분해서 처리 — 장애를 정상으로 오인해 조용히 넘어가는 것 방지
