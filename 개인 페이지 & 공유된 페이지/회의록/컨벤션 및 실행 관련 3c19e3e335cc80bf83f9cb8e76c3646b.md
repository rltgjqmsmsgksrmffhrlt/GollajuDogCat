### 패키지 구조

```sql
ecommerce-platform/

│       ├── 0001-common-event-scope.md    # common-event 모듈 사용 범위 제한 규칙
```

- **향후 확장 시 패키지 분류 가이드**
    
    새로운 요소를 어디에 넣을지 판단할 때의 가이드
    
    1. 재사용성: 2개 이상의 서비스가 실제로 동일하게 사용하는가? → 아니면 서비스 내부에 둔다.
    2. 성격: 기술적 설정/표준인가, 도메인 로직인가? → 도메인 로직이면 절대 공통 모듈에 넣지 않는다.
    3. 안정성: 변경 빈도가 낮고 계약으로서 안정적인가? → 자주 바뀌면 우선 서비스별로 두고, 패턴이 안정화된 뒤 공통으로 추출
    
    | 신규 요소 (예상..) | 배치 위치 | 이유 |
    | --- | --- | --- |
    | Redis (캐시) | `modules/common-cache` (신규 모듈) | 재사용성 높은 기술 표준, 사용 안 하는 서비스가 억지로 의존하지 않도록 별도 모듈 |
    | Config Server 연동 | 각 서비스 yml의 `spring.config.import` | 공통 모듈화할 코드가 거의 없음 |
    | Eureka | 각 서비스에 개별 추가, 확정되면 공통 추출 검토 | 인프라 미확정 상태에서 성급한 추상화 방지 |
    | 신규 마이크로서비스 | `services/` | 원칙 유지 |
    | 신규 이벤트 스펙 | `modules/common-event` 서브패키지, 버전 관리 필수 | 2장 규칙 유지 |
    | 모니터링 대시보드 | 미정 (인프라팀 결정 후 별도 논의) |  |

### 서비스 내부 구조 (헥사고날 예시) (구조 확정은 아니고 예시입니다!_

```
order-service/
├── build.gradle
├── src/main/java/com/company/order/
│   ├── OrderServiceApplication.java
│   ├── domain/                          # 순수 도메인 모델 (프레임워크 비의존)
│   ├── application/                     # 유스케이스 + port(in/out)
│   ├── adapter/
│   │   ├── in/web/
│   │   ├── in/messaging/
│   │   ├── out/persistence/
│   │   └── out/messaging/
│   └── config/
└── src/main/resources/
    ├── application.yml
    ├── application-local.yml
    └── application-prod.yml
```

DDD 4-Layer를 선호하는 팀원은 `adapter`를 `presentation/infrastructure`로 이름만 바꿔도 무방. (원칙은 `domain`이 프레임워크에 의존하지 않는다는 것)

## 프로젝트 실행 방법 (local, docker-compose)

### 인프라 실행

```bash
docker compose -f local-infra/docker-compose.yml up -d
```

```bash
docker compose -f local-infra/docker-compose.yml --profile monitoring up -d
```

### 전체 서비스(인프라 포함) 통합 실행

```bash
docker compose --profile all up --build
```

### 특정 서비스만 실행

```bash
docker compose --profile <서비스> up -d --build
```

```bash
docker compose --profile <서비스1> --profile <서비스2> up -d --build
```

profile 관련해서는 docker-compose의 각 서비스의 profiles 항목 참고!

### 기존 환경에서 새 서비스(DB) 추가 시

`local-infra/postgres/init.sql`은 PostgreSQL 컨테이너가 **처음 생성될 때(빈 볼륨)만** 실행됩니다.
이미 `postgres-data` 볼륨이 있는 상태에서 새 데이터베이스가 init.sql에 추가되면 자동 반영되지 않습니다.

- 로컬 더미 데이터라 지워도 무방한 경우: `docker compose -f local-infra/docker-compose.yml down -v` 후 재기동
- 기존 데이터를 유지해야 하는 경우: `psql`로 직접 `CREATE DATABASE {name}_db` 실행

+게이트웨이 라우팅 확인 완료 (각 서비스 8080으로도 접근 가능)
