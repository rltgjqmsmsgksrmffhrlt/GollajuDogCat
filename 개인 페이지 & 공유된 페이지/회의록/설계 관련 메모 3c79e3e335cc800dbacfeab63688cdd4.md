# 시원

**마이크로 서비스 구성 관련 AI랑 얘기한 내용**

- Q1. 상품과 재고, 같은 서비스에서 관리하는 게 맞나?
    
    **결론: "완전히 같은 서비스"도, "처음부터 완전히 분리"도 아닌, "같은 서비스 내에서 별도 애그리거트/모듈로 분리해서 시작"을 권장합니다.**
    
    업계에서 실제로 자주 나오는 실패 사례는 반대 방향입니다. product-service가 카탈로그·재고·가격·프로모션을 전부 하나의 공유 DB에 몰아넣었다가 "분산 모놀리스"가 되는 패턴이 흔히 언급되며, 개선된 형태로는 catalog-service와 inventory-service를 책임(재고 추적/예약 vs 상품정보/카테고리)과 DB를 분리하는 예시가 제시됩니다.catalog-service는 상품정보/카테고리/검색을, inventory-service는 재고 추적/예약을 담당하고 각각 별도 DB를 가지는 구조가 개선 사례로 제시됩니다 [Medium](https://medium.com/@asmaamofarid/microservices-series-service-boundaries-databases-and-principles-61a6842ca2d5)
    
    이렇게 나누는 이유는 두 도메인의 **읽기/쓰기 특성과 정합성 요구가 다르기 때문**입니다.
    
    - 카탈로그: read-heavy, 캐시 가능, 변경 빈도 낮음, eventual consistency로 충분
    - 재고: write-heavy, 동시성 제어 필요(특히 타임딜처럼 순간 트래픽 몰릴 때), 강한 정합성 필요
    
    다만 처음부터 완전히 분리된 서비스(별도 배포 단위, 별도 DB, 별도 팀 온콜)로 시작하는 것은 신중해야 합니다. *Building Microservices*의 조언처럼, 숙련되기 전까지는 새 시스템을 조금 더 모놀리식 쪽에 가깝게 두고, 서비스 경계를 잘못 설정하는 비용이 크기 때문에 도메인이 안정화될 때까지 기다리는 것이 합리적입니다 지금 단계에서 도메인 경계가 완전히 검증되지 않은 상태이므로, [GeeksforGeeks](https://www.geeksforgeeks.org/system-design/saga-design-pattern/)
    
    - **1단계(권장)**: `product-service` 안에 `Product`(카탈로그) 애그리거트와 `Inventory`(재고) 애그리거트를 **명확히 분리된 모듈/패키지/테이블**로 설계 (재고 갱신 로직은 별도 도메인 서비스로, 트랜잭션 경계도 분리)
    - **2단계(트래픽 확인 후)**: 타임딜 등으로 재고 갱신 트래픽이 카탈로그 조회 트래픽과 스케일링 특성이 크게 벌어지면 `inventory-service`로 물리적 분리
    
    이렇게 하면 나중에 분리할 때도 이미 애그리거트 경계가 명확하므로 마이그레이션 비용이 적습니다.
    
- Q2. 리뷰를 상품과 별도 서비스로 나누는 게 적합한가?
    
    **적합하다고 봅니다.** 별도 서비스로 분리하세요.
    
    서비스 경계를 정하는 실용적 기준 중 하나는 "변경 속도"입니다. 두 기능이 항상 함께 변경된다면 같은 서비스에 두는 것이 맞지만, 변경 속도가 다르거나 다른 팀이 담당한다면 분리하는 것이 타당합니다. 예를 들어 카탈로그는 한 달에 한 번 정도 변경되어 안정적인 반면 체크아웃은 매주 변경되는 경우, 카탈로그 변경이 체크아웃 배포를 막지 않도록 분리하는 것이 좋습니다
    
    리뷰 도메인은 이 기준에서 상품 카탈로그와 성격이 다릅니다:
    
    - 리뷰 요약(AI), 리뷰 필터, 신뢰도 표시 등 **기능이 계속 추가/변경될 영역**인데, 카탈로그는 상대적으로 안정적
    - 리뷰는 **AI 팀 리포지토리와의 연동 지점**이 많습니다 (긴 리뷰 요약, 기호성/변/피부/체중 반응 분류 등). 이 인터페이스가 product-service 내부에 있으면 AI 팀과의 계약 지점이 애매해지고, product-service 배포가 리뷰 관련 AI 기능 변경에 발목 잡힐 수 있습니다
    - 리뷰는 상품뿐 아니라 반려동물 프로필(member), 구매 이력(order)을 참조하는 **cross-domain 집계 성격**이 강해서, 오히려 독립된 컨텍스트로 두고 이벤트/API로 필요한 데이터를 가져오는 편이 깔끔합니다
- Q3. 장바구니는 상품 도메인에 포함하는 게 맞나?
    
    **아니요. 상품(product) 서비스에는 포함하지 않는 것을 권장합니다.**
    
    실제 이커머스 참조 아키텍처에서도 Cart Service는 Catalog Service와 별개의 마이크로서비스로 분리되어, 사용자가 체크아웃 전 아이템을 담고 빼고 수정하는 역할을 담당합니다 [Learnixo](https://learnixo.io/courses/system-design/microservices-service-boundaries)
    
    이유:
    
    - 장바구니는 세션성/휘발성 데이터(자주 바뀌고, 만료되고, Redis 같은 빠른 KV 스토어가 더 적합한 경우가 많음)인 반면, 상품 카탈로그는 영속적 관계형 데이터
    - 장바구니 담당 로직(가격 재계산, 프로모션 적용, 재고 임시 예약 여부 등)은 결제/주문 플로우와 훨씬 밀접함
    - product-service 팀(카탈로그 담당)이 체크아웃 관련 도메인 로직까지 떠안게 되면 책임 범위가 흐려짐
    
    **대신 두 가지 선택지가 있습니다:**
    
    - **A안(권장)**: `order-service`에 포함 — 장바구니를 "PENDING 상태의 주문"으로 모델링. PRD 2.1.6에서 언급한 "개인화 추천 → 바로 결제(뎁스 줄이기)"라는 UX 목표를 생각하면, 체크아웃 크리티컬 패스에서 서비스 간 호출을 줄일 수 있어 유리합니다.
    - **B안**: 독립된 `cart-service` — 다만 지금 도메인 규모에서는 오히려 서비스만 늘리고 체크아웃 시 호출 홉만 늘어날 가능성이 있어 신중히 판단하세요.
- Q4. 상점 도메인은 어디에 위치해야 하는가? 상점 정보를 member에서 관리해도 되는가?
    
    이 부분이 가장 중요하게 **PM/PD와 재확인이 필요한 지점**이라고 생각합니다. 먼저 원칙적인 답부터 드리면:
    
    **상점(Shop) 정보를 member 서비스에 넣는 것은 권장하지 않습니다.**
    
    DDD 관점에서 Bounded Context를 나누는 핵심 기준은 "같은 실세계 개념도 관점(팀)에 따라 다른 모델을 가질 수 있다"는 것인데, 지금 케이스는 그보다 더 단순합니다 — Member(반려동물 보호자/구매자)와 Shop(사업자)은 **애초에 서로 다른 실세계 엔티티**입니다. 두 서브시스템을 위해 단일 모델을 만들면 불필요한 복잡성이 생기고, 여러 팀을 동시에 만족시켜야 하므로 시간이 지날수록 모델을 발전시키기 어려워집니다. 따라서 같은 실세계 엔티티라도 서로 다른 컨텍스트에서는 별도의 모델로 설계하는 것이 낫습니다 하물며 Member와 Shop은 애초에 같은 엔티티도 아니므로(고객 PII 모델 vs 사업자 정산/심사 모델), 억지로 한 서비스에 합치면 향후 사업자 등록 심사, 정산 계좌, 상점 운영정책 같은 기능이 늘어날 때 member-service가 계속 비대해집니다. [Semaphore](https://semaphore.io/blog/domain-driven-design-microservices)
    
    **제안:**
    
    - **신규 `shop-service` 도메인**을 만들어 상점 프로필, 사업자정보(사업자등록번호, 주소, 연락처), 정산 계좌, 상점 카테고리/운영정책, 상점 승인·심사 상태를 관리
    - 상점 관리자의 **로그인 자격증명(인증)** 자체는 기존 `auth-service`가 계속 담당 (Member든 상점 관리자든 "인증"이라는 관심사는 동일)
    - 상점 관리자가 **어느 상점에 속하고 어떤 권한(role)을 가지는지**는 `shop-service`가 소유하는 편이 자연스럽습니다 (auth는 "누구인지 증명"까지, "무엇을 할 수 있는지"는 각 도메인이 관리하는 편이 일반적인 관심사 분리)
    - `product-service`는 상품에 `shopId`만 참조하고, 상점 상세정보가 필요하면 API/이벤트로 조회
    
    **다만 이 제안 이전에 확인이 꼭 필요한 것:**
    
    PRD에는 "서비스는 기획상 B2C"라고 되어 있는데, 동시에 "상점 상위 개념 + 상점 관리자 role"이 존재한다고 하셨습니다. 이 조합은 실제로는 **입점 판매자가 여러 명 존재하는 마켓플레이스(오픈마켓) 구조**일 가능성이 있습니다. 만약 그렇다면:
    
    - 판매자별 **정산(settlement)** 로직이 필요해져 payment-service의 범위가 커집니다 (단순 PG 연동이 아니라 판매자별 매출 배분/수수료 정산까지)
    - 상품 등록/승인 워크플로우, MD 심사 등 운영 도메인이 추가로 필요할 수 있습니다
    - 반대로 "상점"이 자사 브랜드/카테고리 구분용 개념(예: 자사몰 내 브랜드관)이고 판매자가 실질적으로 1개(자사)뿐이라면, shop-service를 독립 서비스로까지 분리할 필요 없이 product-service 내 하위 애그리거트로 둬도 충분합니다.
    
    이 구분에 따라 서비스 경계와 payment-service 범위가 크게 달라지므로, 설계를 확정하기 전에 PM/PD에게 "상점이 다중 판매자 구조인지, 자사 단일 운영 구조인지"를 반드시 확인하시길 권합니다.
    
- Q5. 기타 필요한 도메인
    
    PRD를 다시 훑어보면 명시적으로 서비스화되지 않았지만 짚어야 할 도메인들이 있습니다.
    
    - **프로모션/타임딜/쿠폰**: 지금은 product 하위로 뒀지만, 할인 규칙이 복잡해지면(쿠폰 중복적용, 등급별 할인 등) 별도 애그리거트로 분리될 소지가 큽니다. 지금은 product-service 내부 모듈로 시작해도 무방합니다.
    - **배송/교환/환불(Fulfillment)**: PRD 2.2 플로우에 "배송 취소/위치", "교환/환불/문의"가 나오는데 이는 order와 payment 양쪽에 걸친 도메인입니다. 별도 서비스보다는 order-service 내 하위 상태 전이로 두되, 환불이 발생하면 payment-service와 SAGA로 연동하는 구조가 필요합니다.
    - **구매 후 체크인/피드백(2.1.4)**: 리뷰와는 결이 다릅니다(리뷰=공개 콘텐츠, 체크인=개인화 데이터/AI 추천 피드백 루프용). review-service에 통합하거나, AI 팀 추천 로직과의 연계를 고려해 별도 애그리거트로 두는 걸 검토해보세요. 어느 쪽이든 이 데이터가 AI 팀 레포로 이벤트 발행되어야 한다는 점은 미리 인터페이스를 정의해둬야 합니다.
    - **검색(자연어 검색, 2.1.5-5)**: 이 기능이 AI 팀 레포(LLM 프롬프트 기반)에서 처리되는지, 백엔드가 Elasticsearch 등으로 별도 search-service를 운영하는지 팀 간 역할 분담이 필요합니다.
    - **파일/이미지(반려동물 사진, 상품 이미지)**: 별도 서비스라기보다 공용 인프라(S3+CDN) 영역으로 보는 게 일반적입니다.

    | **payment-service** | 결제수단 관리, PG 연동, 결제 트랜잭션, 환불, (마켓플레이스면) 정산 | order와 SAGA(오케스트레이션/코레오그래피)로 연동 |

주문–결제–재고처럼 여러 서비스 DB에 걸친 트랜잭션은 각 서비스가 독립 DB를 갖는 이상 단일 ACID 트랜잭션으로 묶을 수 없으므로, SAGA 패턴(주문 생성 → 재고 예약 → 결제 처리, 실패 시 보상 트랜잭션으로 재고 반납/결제 취소)으로 설계하시는 걸 권합니다. 이 패턴은 분산 트랜잭션 없이도 여러 서비스에 걸친 데이터 일관성을 유지할 수 있게 해줍니다 특히 타임딜처럼 동시성이 몰리는 시나리오는 재고 예약 단계의 락 전략이 SAGA 설계에 큰 영향을 줍니다. - 주의사항 / PRD 변경 시 영향받을 부분
    - **상점 구조가 마켓플레이스로 판명될 경우**: payment-service 범위가 정산까지 확장되고, product-service의 승인 워크플로우가 추가되어 지금 제안한 경계가 상당 부분 바뀝니다. 가장 먼저 확인해야 할 항목입니다.
    - **재고 동시성 요구 수준**: 타임딜 트래픽 규모에 따라 product-service 내 재고 모듈을 조기에 별도 서비스로 분리해야 할 수도 있습니다. 부하 테스트 전에는 "분리 가능한 구조"로만 설계해두고 확정 짓지 마세요.
    - **진료내역 등 민감정보**: PRD에 `확인필요(보안)`로 표시된 부분입니다. 개인정보/의료 관련 데이터 취급 기준(암호화, 접근통제, 보존기간)은 법무·보안 검토가 별도로 필요하며, 이 결과에 따라 member-service의 데이터 모델과 접근 정책이 바뀔 수 있습니다.
    - **리뷰 신뢰도 표시(구매횟수/사용기간)**: review-service가 order-service 데이터에 의존하므로, 실시간 API 호출로 할지 이벤트 기반으로 비동기 동기화할지 결정이 필요합니다. 리뷰 조회 트래픽이 많다면 이벤트 기반 동기화(읽기 모델을 review-service에 복제)가 유리합니다.
    - **AI 팀과의 인터페이스 계약**: 리뷰 요약, 성분 분석, 자연어 검색, 추천 등 AI 결과를 어느 서비스가 저장/캐싱하고, 어떤 이벤트/API로 데이터를 주고받을지 초기에 AI 팀과 스키마 수준으로 합의해두지 않으면 review-service와 product-service의 경계가 자주 흔들릴 수 있습니다.
    - **배송지 정보의 시점 문제**: member-service의 배송지가 "재사용 가능한 템플릿"인지, 주문 시점의 "스냅샷"인지 구분해서 설계해야 합니다. 이걸 명확히 안 하면 회원이 배송지를 수정했을 때 과거 주문의 배송지 정보까지 바뀌어버리는 데이터 무결성 문제가 생깁니다.

### 타임딜 관련 논의 내용

```html

19:50 사전 Scale-out → 20:00 타임딜 시작 → 사용자 동시 접속 및 구매 요청 증가 → Queue를 통한 요청 처리 → 트래픽 증가에 따라 추가 Scale-out → 한정 수량 소진 또는 타임딜 종료 → 트래픽 감소 후 Scale-in

타임딜을 구체화하기 위해 필요한 항목들을 아래와 같이 정리했습니다.

• 타임딜 시간: 타임딜 시작·종료 시각 및 진행 시간
→ 목요일 저녁 8시부터 30분간

→ 개 사료 3종, 고양이 사료 3종 총 6종 / 

• 타임딜 아이템 선정 기준: **어떤 기준으로 타임딜 상품을 선정할지 정의**
→ 최근 구매량이 많은 인기 상품 선정 (초기 서비스니까 신규 사용자 유입을 위해 인기 상품 할인)

• 상품별 한정 수량: 각 타임딜 상품별 판매 가능한 수량
→ 상품별 200개

• 1인당 구매 수량 제한: 동일 사용자가 구매할 수 있는 동일 상품 수량
→ 상품별 1인 1개

• 1인당 구매 가능 상품 종류: 동일 사용자가 구매할 수 있는 타임딜 상품 1인당 1종류로 제한

• 결제 방식: 타임딜 상품의 결제 처리 방식
→ 기존 일반 상품과 동일한 결제 방식 사용

• 할인율: **타임딜 대상 상품에 적용되는 할인 비율**
→ 정상가 대비 29% 할인

• 사용자 진입 방식: 사용자가 타임딜을 발견하고 접근하는 경로
→ 메인 배너 클릭 + 알림 → 타임딜 전용 페이지 → 상품 상세 페이지

• 사전 트래픽 대응: 타임딜 시작 시각이 정해져 있으므로 트래픽 급증에 대비한 사전 대응 방식
→ 타임딜 시작 전 일부 Pod를 사전 확장하여 초기 트래픽 증가에 대응

→ 타임딜 시작 후 구매 요청이 집중될 경우 Queue를 활용하여 요청을 순차적으로 처리

→ 요청량이 증가할 경우 Queue 상태 또는 서비스 부하를 기준으로 Pod를 추가 확장

• 타임딜 종료 조건: 타임딜이 종료되는 조건
→ 한정 수량 소진 또는 타임딜 시작 후 30분 경과 시 종료
```
