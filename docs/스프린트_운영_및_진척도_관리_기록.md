### 운영 원칙

1. **진행 상황은 결과 중심으로 공유한다** — 무엇을 했는지가 아니라 어떻게 진행했고 어떤 결과가 나왔는지까지 공유한다. (08/31 운영 방식 변경)
2. **의존사항은 문서화한다** — 구두 협의로 끝내지 않고 담당자·기한·상태를 기록한다. (08/18 결정)
3. **기획 변경은 영향 범위까지 확인한다** — IA·기능명세서·와이어프레임·API 명세의 동기화 여부를 함께 확인한다. (09/01·09/03 적용)
4. **기술적 제약은 MVP 범위에 반영한다** — 구현이 불가능하거나 비용 대비 효율이 낮은 기능은 범위를 조정한다. (08/28·09/11 적용)
5. **회고 결과는 다음 스프린트 운영 방식에 반영한다** — 같은 문제가 반복되지 않도록 운영 규칙 자체를 바꾼다.

### 상태 라벨 정의

기록의 신뢰도를 위해 "결정한 것"과 "실제로 해결된 것"을 구분한다.

| 라벨 | 의미 |
| --- | --- |
| **결정** | 방향이 합의되어 확정된 사항 |
| **조치** | 담당자가 실제로 행동한 사항 (문서 공유, 기한 지정, 규칙 신설 등) |
| **해소** | 블로커가 실제로 해제되어 후속 작업이 시작된 사항 |
| **진행 중** | 요청·협의 단계로, 아직 확정되지 않은 사항 |
| **이월** | 다음 스프린트 또는 이후 논의로 넘긴 사항 |

### 3.3 Sprint 1 Retrospective

*근거: 08/14 · 08/21 팀장 주간 미팅*

**Keep**

- 완성도를 높인 뒤 공유하기보다 **빠른 초안을 만들어 공유**하고 피드백을 반영하는 방식으로 진행했다. (PM)
- 페인포인트와 직접 연결된 설문·인터뷰를 설계해 실제 사용자 문제를 확인했고, 결과가 가설과 일치해 정리가 수월했다. (PM·PD)
- PM이 노션 문서를 구조화해 두어 타 직군의 산출물 활용이 편했다. (PD)
- 역할 분배가 명확해 계획한 산출물을 완료했다. (FE·인프라)
- 법률 업무 경험자가 주도하고 나머지가 서브하는 방식으로 생소한 영역의 진입 장벽을 해소했다. (보안)

**Problem**

- 기능 정의 미팅이 길어져 **일정이 지연**되었고, 기능이 방대해 정리가 필요했다. (PM)
- 일정이 약 0.5일 지연되었고 WBS가 PM·FE와 중복되었다. (PD)
- **기획 미확정으로 AI 개발 착수 시점이 불명확**했고, 재구매 예측 기능의 목적이 PM 기획과 달라 산출물 수정을 보류했다. (AI)
- 갑작스러운 인원 공백과 일정 이슈 미체크가 겹쳐 혼란이 있었다. (보안)
- **사용 리소스 미확정으로 예상 비용을 산출할 수 없었다.** (인프라)
- PRD 작성 주체, AI 데이터 저장 형태(PostgreSQL vs MongoDB) 등 기본 전제가 합의되지 않은 채 각자 진행되었다. (BE)

**Try**

- 기능 상세화 이전에 **MVP 범위와 우선순위표를 먼저 합의**한다.
- 기획에 묶인 작업과 **선행 가능한 작업을 분리**한다.
- 팀 간 의존·대기 관계를 **WBS·문서에 명시**한다.
- 기능별 예상 개발 리소스(Man/Month)를 함께 산정한다.
- 결원·공가를 주간 단위로 사전 취합한다.

### 4.3 Sprint 2 Retrospective

*근거: 09/04 팀장 주간 미팅 + 데일리 스크럼 (08/28 회차 주간 미팅 기록은 남아 있지 않아 데일리 스크럼으로 보완)*

**Keep**

- PM 내부 분업으로 **Phase 2 문서와 서비스 설계를 병행**했고, PD와 싱크를 맞추며 MVP 범위 내 설계를 마무리했다. (PM)
- PM↔PD 싱크 작업으로 **기획과 다른 디자인이 나오는 상황을 예방**했다. (PD)
- 계획한 일정대로 진행되었고 역할 분담이 원활했다. (FE)
- 작업 결과를 **크로스 체크하며 서로 보완**했다. (보안)
- 팀원 결석이 있었으나 **사전 백업으로 진행에 지장이 없었다.** (PM)

**Problem**

- 일정이 2일 지연되었다. (PD)
- **BE 설계 완료가 지연**되어 구현 착수가 순연되었다. (08/28)
- **AI↔BE 인터페이스 명세가 늦어** 통신 구조(FastAPI 사용 여부, 데이터 전달 방식)를 확정하지 못했다. (BE)
- 백오피스·관리자 관점 정의가 없어 관련 질문이 반복되었다. (BE ↔ PM)
- IA·와이어프레임과 실제 구현 범위에 차이가 있어 범위 정리에 시간이 소요되었다. (08/28)
- 협업 도구가 분산되어 진행 상황 파악이 어렵다는 지적을 받았다. (08/31 강사 피드백)
- 주간 미팅 기록에 **관리자 계정 자격증명이 평문으로 기재**되었다. 산출물·회의록에 자격증명이 남는 것은 보안 위험이다. (09/04)

**Try**

- 양방향 인터페이스는 **스프린트 초반에 담당·기한을 정해 문서로 교환**한다.
- 기획 변경 시 영향받는 산출물의 **동기화 담당자와 기한을 함께 지정**한다.
- 구현 가능 범위는 **기능명세서를 단일 기준**으로 삼는다.
- 진행 상황은 도구를 분산하지 말고 데일리 스크럼에서 **작업 방식과 결과까지 공유**한다.
- **자격증명은 문서·회의록에 남기지 않고** 별도 수단으로 전달하며, 이미 노출된 계정은 교체한다.

### 5.3 Sprint 3 중간 회고 (09/16 기준)

> **Sprint 3은 09/18 종료 예정으로, 아래는 확정 회고가 아닌 중간 회고이다.**
> 근거는 09/11 팀장 주간 미팅과 09/16까지의 데일리 스크럼이며, 확정 회고는 09/18 팀장 주간 미팅 이후 갱신한다.

**Keep**

- **데이터 수집 계획서를 사전에 구체화**해 90일 가상 운영 데이터 생성과 퍼널·코호트 분석까지 연결했다. (PM, 09/11)

**Problem**

- PD는 일정 압박으로 **주말 작업이 필요**했고 부담이 특정 직군에 집중되었다. (PD, 09/11)
- **결원이 많아 협업이 어려웠다.** (AI, 09/11) PM도 주중 2일 결원이 있었다.
- FE가 **디자인 시스템 → UI 디자인 → API 명세** 순의 선행 산출물에 연속으로 묶여 09/15까지 화면 구현 착수가 지연되었다.

## 7. PM 운영 관점 핵심 사례

### ① 기획 미확정 상태의 개발 착수를 보류하고 선행 작업을 분리 — 의존성 관리

**상황 (08/18)** — 생성형 AI 기능 3개의 유지 여부에 직군별 의견이 갈렸고, BE는 시간 손실을 우려해 즉시 구현 착수를 주장했다. 강사는 설계·기획 확정 전 구현 시 데이터 스키마 재작업 위험을 지적했다.
**조치** — 메인 기능 3개 중 재구매 예측만 교체하기로 정리하고, AI의 작업을 '실제 구현'과 '후보안·레퍼런스 조사'로 분리해 구현은 설계 확정까지 보류했다.
**결과** — 기획 변경에 따른 재작업 없이 AI팀이 선행 가능한 작업을 계속 진행했다. 같은 날 "팀 간 의존 관계를 구두가 아닌 문서로 기록한다"는 원칙도 함께 수립되어 Sprint 2 스크럼 양식에 반영되었다.

### ② 구현 가능 범위 기준으로 MVP를 축소 — Scope Management

**상황 (08/28)** — IA·와이어프레임에 쿠폰, 입점·제휴 문의, 리뷰 신고, 고객센터, 재입고·타임딜 푸시 알림 등 BE가 구현할 수 없는 기능이 포함되어 있었다.
**조치** — 기능명세서를 구현 범위의 단일 기준으로 삼고, 해당 기능을 제외 또는 후순위로 정리했다. 09/03에는 "와이어프레임의 목업 UI는 실제 기능이 아니며 기능 유무는 기능명세서·IA로 판단한다"를 전체 공지했다.
**결과** — 설계 단계에서 반복되던 범위 확인 질문이 정리되고, 구현 대상이 확정된 상태로 Sprint 3 개발에 진입했다.

### ③ 5개 직군 간 인터페이스를 축별로 관리 — Cross-functional Coordination

**상황 (09/02 ~ 09/04)** — 직군별 산출물이 독립적으로 진행되어 BE↔AI 등 후속 개발을 막는 상황이 발생했다.
**조치** — 인터페이스를 `PD↔FE(핸드오프)` / `BE↔FE(API 계약)` / `CN↔CI(클러스터 환경)` / `Sec↔BE·CN(인증·보안 정책)` / `AI↔BE·FE(추론 통합)` 5개 축으로 구분하고, 축별 산출물과 제출 기한(09/04)을 지정했다. Sprint 3에서는 같은 5개 축으로 Phase 3 공통 산출물 기한(09/17)을 다시 지정했다.
**결과** — 09/04 기준 5개 축 중 3개 완료, 1개 당일 제출, 1개 이월로 **상태가 축별로 추적 가능**해졌다. 미완료 항목도 담당과 기한이 명시된 상태로 남았다.

### ④ 기술적 제약을 제품 의사결정으로 전환 — 기술 제약 반영

**상황 (09/11)** — 추천 API가 `pet_id` 기준으로 전체 상품에서 추천하는 구조여서, 검색 결과 집합 안에서 추천순으로 재정렬하는 기능은 구현이 어려웠다.
**조치** — 구조를 BE·AI와 함께 확인한 뒤 기능을 억지로 구현하지 않고, 추천순 정렬을 기본 목록 조회에만 적용하고 검색에서는 제외하기로 결정했다.
**결과** — 스프린트 내 완결 가능한 범위로 조정되었다. 같은 원칙이 09/15 타임딜 '1일 섭취 기준 가격'에도 적용되어, 근거 데이터가 없는 값을 추정하지 않고 null 처리 후 우선 구현하는 방식으로 정리했다.

### ⑤ 회고 결과를 운영 규칙 변경으로 연결 — Continuous Improvement

**상황** — Sprint 1 회고에서 나온 문제(우선순위 기준 부재, 구두 의존성, 협업 정보 분산)가 반복될 경우 설계·구현 단계에서 비용이 커지는 구조였다.
**조치** — 회고 항목을 다음 스프린트의 운영 규칙으로 전환했다. RICE·Man/Month 산정 도입(08/21), 스크럼 양식에 블로커/의존성 상설화(Sprint 2), 공유 형식을 '무엇을/어떻게/결과'로 변경(08/31), 인터페이스 축별 기한 지정(09/02·09/14), 변경 증빙을 PR 이력으로 전환(09/16 제안).
**결과** — 3개 스프린트에 걸쳐 **운영 체계 수립 → 설계 체계화 → 구현 단계 의존성 관리**로 운영 방식이 단계적으로 이동했다. (6장 표 참조)

> 담당·기한·대안을 정해 일정과 MVP에 미치는 영향을 통제하는 것이었다.
> 위 기록의 '진행 중'·'이월' 항목은 그 통제 대상이 현재 어디에 있는지를 그대로 보여준다.
