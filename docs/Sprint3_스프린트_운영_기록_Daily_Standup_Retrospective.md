## 3.3 Sprint Retrospective

### Keep

- 팀장 데일리 스크럼에서 **직군별 '도움 필요 사항'을 매일 명시적으로 남기고 다음 날 회신**하는 방식이 정착되어, 대부분의 의존 요청이 1일 내 응답되었다.
- 회의록에 **블로커/의존성(우리가 기다리는 것 / 다른 팀이 기다리는 것)** 섹션을 고정 항목으로 두어, 선행 의존 관계가 계획 단계에서 드러났다.
- 09/08 UI 지연 대비 fallback(와이어프레임 기준 산출물 작성)처럼 **지연 시 대안을 미리 합의**해 두어 일정 리스크가 산출물 리스크로 번지지 않았다.
- 기술적 제약이 확인되면 **기능 범위를 축소해서라도 스프린트 내 완결**시키는 결정(검색 내 추천순 제외, 타임딜 필드 null 처리)을 빠르게 내렸다.

### Problem

- FE가 **디자인 시스템 → UI 디자인 → API 명세** 순의 선행 산출물에 연속으로 묶여, 2주차 중반(09/15)까지 화면 구현 착수가 지연되었다.
- **API 명세의 수정 주체가 FE·BE로 이중화**되어 있어 09/11에야 일원화 협의가 이루어졌고, 그전까지 명세 싱크 어긋남 리스크가 있었다.
- **AI ↔ BE 인터페이스 명세 공유가 스프린트 후반(09/17)으로 밀리면서** BE의 AI 연계 기능 개발이 마지막 이틀에 집중되었다.
- 직군별 이슈·블로커가 **각 회의록에만 흩어져 있어** Phase 3 산출물 작성 시점(09/14)에 소급 취합해야 했다.
- 공가·부재가 **당일 스크럼에서 공유**되는 경우가 있어(09/08 PM↔PD 싱크 순연) 협업 일정이 즉시 순연되었다.
- 인터뷰 피드백에서 지적된 것처럼 **직군별 전문용어가 타 직군에 그대로 전달**되어 의사결정 속도가 떨어지는 구간이 있었다.

### Try

- 인터페이스(명세·계약) 변경은 **단일 오너를 지정하고 PR 단위로 동기화**한다 — API 명세는 BE, 디자인 핸드오프는 PD가 오너.
- 의존 요청은 **"무엇을 / 누구에게 / 언제까지"** 형식으로 기한을 명시해 기록한다(09/14 AI API 기한 합의 방식을 표준화).
- 블로커 트래킹 표를 **스프린트 시작 시점부터 상시 운영**하고, 데일리 스크럼에서 상태만 갱신한다(스프린트 종료 후 소급 취합 금지).
- 선행 산출물 의존이 있는 과업은 **착수 가능한 최소 단위(와이어프레임·목데이터 기준)를 병행 진행**해 대기 시간을 줄인다.
- 공가·부재는 **전주 금요일 주간 미팅에서 사전 공유**하고 주차 계획에 반영한다.
- 타 직군 대상 공유 시 **전문용어에 1줄 설명을 병기**한다.
