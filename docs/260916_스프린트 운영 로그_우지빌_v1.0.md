# 2. 개요

> 본 문서의 목적은 스프린트 단위로 직군별 진행 상황과 의존사항을 공유하고, 개발 과정에서 발생한 블로커를 조기에 발견, 조율하여 일정과 MVP 범위를 관리한 과정을 기록함에 있다. 또한, 각 스프린트의 회고 결과를 다음 스프린트 운영 방식에 반영하여 협업 프로세스를 개선한 이력까지 함께 남긴다.

# 3. 운영 구조

| 주간 회고 미팅 | 주간 회고로 반복 문제와 개선점 도출 | 매주 금요일 팀장 주간 미팅 |
| 협의 미팅 요청 | 직군 간 문의, 협의, 협상 사항 공유 및 합의를 위한 미팅 시간 조율 | 필요 시 직군별로 신청 |

## 3.1 운영 원칙

- **진행 상황은 결과 중심으로 서면 기재로 공유**: 무엇을 했는지뿐 아니라 어떻게 진행했고 어떤 것을 고려했으며 어떤 결과가 나왔는지 기록
- **서비스 및 기능 변경은 영향 범위까지 확인**: IA, 기능명세서, 와이어프레임, API 등 관련 산출물의 동기화 여부 확인
- **기술적 제약은 MVP 범위에 반영**: 구현 불가능하거나 비용 대비 효율이 낮은 기능은 범위를 조정

# 10. PM 운영 관점 핵심 사례

#### ① 기획이 확정되지 않은 기능은 구현을 멈추고, 먼저 할 수 있는 작업을 분리

**상황 (08/18)** : 생성형 AI 기능 3개의 유지 여부를 두고 직군별 의견이 달랐다. **강사 피드백을 통해 기획이 변경될 경우 데이터 구조까지 다시 작업해야 할 위험이 확인됐고**, BE는 개발을 바로 시작하려는 상황이었다.

**조치** : 3개 기능 중 **재구매 예측만 변경**하기로 정하고, AI팀의 작업을 **'실제 기능 개발'과 '후보안·레퍼런스 조사'로 나눴다.** 기능 개발은 기획이 확정될 때까지 보류하고, 그동안 조사·설계처럼 먼저 할 수 있는 작업을 진행했다.

**결과** : 구현·스키마 단계의 재작업은 피했고, **기획 변경에 따른 개발 계획서 수정은 별도로 발생했다.** AI팀도 대기 기간 동안 조사·설계를 계속 진행할 수 있었다. 또한 같은 날 직군 간 의존사항은 말로만 전달하지 않고 문서로 남기기로 했고, 이를 이후 스크럼의 **'블로커/의존성' 항목**에 반영했다.

#### ② 실제 개발할 수 있는 범위에 맞춰 MVP를 줄임

**상황 (08/28)** : IA와 와이어프레임에 쿠폰, 입점·제휴 문의, 리뷰 신고, 고객센터, 재입고·타임딜 푸시 알림 등 **실제 MVP에서 구현 여부를 추가로 판단해야 하는 기능까지 포함**되어 있었다.

**조치** : BE의 구현 범위 관련 요청을 바탕으로 **기능명세서를 실제 개발 범위를 판단하는 기준으로 정리했다.** 09/03에는 와이어프레임의 목업 화면은 실제 개발 기능을 의미하지 않으며, **기능명세서와 IA를 기준으로 기능 여부를 판단한다는 기준을 전체에 공유**했다.

**결과** : 기능 구현 여부를 판단하는 기준이 명확해졌고, **Sprint 3에서는 실제 개발 대상으로 정리된 범위를 기준으로 개발을 진행할 수 있었다.**

#### ③ 직군 간 연결이 필요한 작업을 따로 관리

**상황 (09/02~09/04)** : 강사 피드백으로 5개 직군 간 인터페이스 정의 산출물이 요구되면서, **각 직군의 작업이 서로 어디에 걸려 있는지 정리되지 않은 상태가 드러났다.**

**조치** : 직군 간 연결이 필요한 작업을 `PD↔FE(디자인 전달)` / `BE↔FE(API 전달)` / `CN↔CI(개발 환경)` / `Sec↔BE·CN(인증·보안)` / `AI↔BE·FE(AI 기능 연결)` **5개 영역으로 나누고, 각각 담당자와 제출 기한(09/04)을 정했다.** Sprint 3에서도 같은 기준으로 Phase 3 공통 산출물의 기한(09/17)을 정했다.

**결과** : 09/04 기준 5개 영역 중 **3개 완료, 1개 당일 제출, 1개는 후속 논의로 이월**된 상태로 정리할 수 있었다. 어떤 작업이 끝났고 무엇이 남았는지 영역별로 확인할 수 있게 됐다.

#### ④ 개발상의 제약을 서비스 결정에 반영

**상황 (09/11)** : 추천 API는 `pet_id`를 받아 전체 상품을 대상으로 추천하는 구조라, **검색 결과 안에서 다시 추천순으로 정렬하는 기능은 구현이 어려웠다.**

**조치** : BE가 추천 API 구조를 확인해 검색 내 추천순 정렬 제외를 제안했고, 이를 **기능 범위 조정으로 정리했다.** 추천순 정렬은 기본 상품 목록에서만 제공하기로 했다.

**결과** : 현재 스프린트에서 구현할 수 있는 범위로 기능을 정리했다. 같은 방식으로 09/15 타임딜의 '1일 섭취 기준 가격'도 근거 데이터가 없는 값을 임의로 계산하지 않고 **빈 값(null)으로 처리한 뒤 우선 구현**했다.

#### ⑤ 회고에서 발견한 문제를 다음 스프린트의 운영 방식으로 바꿈

**상황** : Sprint 1 회고에서 **우선순위 기준 부재(08/21)**가, 이후 데일리에서 **의존사항의 구두 공유(08/18)**와 **직군별 정보 분산(08/31 강사 피드백)**이 차례로 확인됐다.

**조치** : 각 문제를 다음 스프린트의 실제 운영 방식에 반영했다.

- 기능 우선순위 → RICE + 개발 소요시간(Man/Month) 비교 (08/21)
- 의존사항 → 스크럼에 블로커/의존성 항목 추가 (Sprint 2)
- 협업 정보 → '무엇을/어떻게/결과' 형식으로 통일 (08/31)
- 직군 간 작업 → 연결되는 작업별 담당자·기한 지정 (09/02·09/14)
- 변경 내용 → 회의록뿐 아니라 PR에서도 변경 이력 확인 (09/16 제안)

**결과** : 3개 스프린트를 거치며 문제를 발견하는 데서 끝나지 않고, **발견한 문제를 다음 스프린트의 운영 방식으로 계속 바꾸는 구조**를 만들었다.
